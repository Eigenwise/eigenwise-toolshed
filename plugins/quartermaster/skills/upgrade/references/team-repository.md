# A team repository or a solo project

The scan says `team` when more than one person committed to the repository, `solo` otherwise. The steps are the same; a line marked **Team** or **Solo** applies to that shape only.

Whatever the shape, a path git tracks (a settings file, committed or local, an old rules or map folder, an instruction file) is never edited or deleted on the plain run and is never on the deletion list. The scan lists those under the one committed-change question, and until the person says yes to it they stay as they are.

A key of a plugin this version has (`sidequest`, `quartermaster`, `codebase-mapper`, `live-rules`) under `eigenwise-toolshed` is this version's own once the update ran, in any file: it is never a leftover and you never touch it, and neither is a project's `extraKnownMarketplaces.eigenwise-toolshed`. A team that wants the older version a while longer pins it themselves: each person removes the marketplace and adds it again as `Eigenwise/eigenwise-toolshed#v1`. The run never does that, and never tells anyone to add a `ref` to an existing entry by hand: in a test that made the marketplace disappear.

Questions: exactly the scan's question line. The gateway question is asked once for the whole machine, not here.

Before the first edit of a settings file, copy it to `<file>.before-upgrade` and say the copy's name. That copy is the undo for every settings step below. When a copy of that name is already there, it is from an earlier day: leave it as it is, never use it as the undo, and name yours `<file>.before-upgrade-<today's date>`.

Old rules need no plugin: Quartermaster converts them (`older-rules.md` beside this file). The map converts with this version's `codebase-mapper:map`; where the mapper is not installed here, `claude plugin install codebase-mapper@eigenwise-toolshed --scope local` first. Where the rules or map plugin was never on, the scan keeps the old rules or map with that reason and lists no step for them.

The scan's line is the one to follow. Where a row below and the scan's verdict could disagree, do what the scan's line says.

A step whose row says "only on a yes" never runs on a "go on". A step with no question carries on without waiting for a reply.

## The review refs command

The same line works in bash and PowerShell. It deletes only refs under the older version's three namespaces whose commits the checked-out branch already has.

```bash
git for-each-ref --merged HEAD --format="delete %(refname)" refs/sidequest/ refs/sidequest-archived/ refs/sidequest-rounds/ | git update-ref --stdin
```
