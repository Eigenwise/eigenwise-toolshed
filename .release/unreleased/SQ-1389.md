title: "A refused release stops before it changes anything"
bump: minor
plugins: []
---

Cutting a release ran the suites, consumed the fragments, wrote the release commit, and created the tags, and only then checked whether CI had passed on the previous main. When that check refused, it left a version commit for a release that never happened, two tags pointing at it, and an empty `.release/unreleased/` whose contents now existed only inside the commit that was not supposed to exist. Recovering meant a hand-driven reset, a cherry-pick to get the fix inside the release rather than after it, and deleting two tags, all while holding the publish lock.

Everything knowable up front is now checked up front, CI included, so a refusal costs seconds and leaves the tree exactly as it was found. That also skips a three and a half minute suite run that was only ever going to be thrown away.

Once the mutating phase does start, a later failure prints the exact commands to undo it rather than attempting a reset that could take working-tree changes with it, including the detail that catches people out: a reset leaves local tags behind, so both commands are needed.

The tag collision message used to say the window "was published (or half-published) before" for any tag it found, which is alarming and usually wrong. It now checks the remote and says which case you are in: a genuinely published tag, or a leftover from an attempt that never got pushed.
