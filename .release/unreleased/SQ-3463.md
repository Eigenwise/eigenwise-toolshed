---
ref: SQ-3463
title: Hold the checkout's index lock while a retired worktree is reclaimed
bump: patch
plugins: [sidequest]
---

Reclaiming a retired checkout now takes that checkout's own `index.lock` before its last HEAD and branch reads and holds it through `git worktree remove`, so a `git commit` (or merge, rebase, checkout, reset) started in the checkout during the reclaim fails with Git's usual "index.lock: File exists" error instead of landing in a checkout that is about to be deleted. When the lock is already held, the reclaim keeps the checkout and its branch and reports `commit_in_progress`.
