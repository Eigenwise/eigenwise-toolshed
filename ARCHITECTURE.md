# Architecture

This is the contract every plugin in this repo builds against. If code and this file disagree, one of them is a bug. Fix it in the same change.

## The five rules

1. **Files are the truth, drawing is a view.** Tickets, proposals, routing tables and rules are plain files a person can read, diff and edit by hand. Panes, bands and toasts only project them. Everything must still work where nothing draws (`claude -p`, an SDK host, a session with mods off).
2. **The main session is the only lifecycle writer.** Subagents get a brief and return one structured result. They never claim, submit, close or touch the board. No tokens, no leases, no identity handshakes.
3. **Git is delivery truth.** The board records what was agreed and what happened. Branches, commits and PRs prove it. Nothing in here adjudicates a merge.
4. **Three decision classes.** What gets built: the human decides, once, only what cannot be undone, spends money or reaches outside the project, or is taste or product direction (the rest is taken and reported), after the agent has investigated; on work that goes through the `plan` skill and changes code, with a person here, also the design a reviewer would argue about on the pull request. How it gets executed: never a question. Changes to the system itself: always offered, approved per item, reversible.
5. **Faster, never heavier.** Zero processes per tool call. Zero model-visible tokens while idle. Every state has an exit the human can take. Signals before gates. See `SCOPE.md` for the admission bar.

## How a plugin is built

Every plugin is a Claude Code plugin. Runtime behaviour lives in one hooks module (a "mod"), behaviour the model follows lives in skills.

```
plugins/<name>/
  .claude-plugin/plugin.json     name, version, description, license, types
  README.md                      the one prose page for this plugin
  hooks/hooks.json               { "modules": ["./register.tsx"] }
  hooks/register.tsx             wiring only: on(event, matcher, hook)
  hooks/*.ts                     pure logic, no `$`, unit-testable
  hooks/*.test.ts(x)             run by `claude plugin test`
  types/index.d.ts               the plugin's `$.state` contract
  skills/<skill>/SKILL.md        short, one job each
  agents/*.md                    only where a role needs its own tool limits
  tsconfig.json
```

Rules for mods:

- No command hooks on `PreToolUse`, `PostToolUse` or `UserPromptSubmit`. In-process hooks only.
- Every gating hook (`tool.call`, `agent.spawn`, `tool.check`, `prompt.submit`, and `session.compact`, which the validator counts as one) has a `.catch`. Ours fail open: a broken hook must never stop the user's work.
- Pure logic goes in plain `.ts` files that take values and return values. `register.tsx` only wires events to them. That keeps every function small and testable without the engine.
- State a drawing reads lives in `$.state` (declared in `types/index.d.ts`). Anything that must survive the session lives in a file. The host only follows a state name that is declared in the file using it, so an atom is never imported from another module: each file names its own, with the same shape tag.
- Never put load-bearing behaviour on `classic.*`, `prompt.compose`, `prompt.section`, `session.compact` or `skill.prompt`. An organisation can switch those off silently. They are fine for sensing.
- The mod API is early access. Pin `engines` in `plugin.json`, and run `claude plugin validate` and `claude plugin test` on every change.

Each plugin is standalone. No plugin lists another under `dependencies`. Where two cooperate, they do it through files or a published `$.state` key, and each works when the other is absent.

## Sidequest contracts

### Board files

The board lives in the project at `.sidequest/`. Its home is found from the session's project root, never from the folder the shell happens to be in: observed 2026-11-22 in a real session, the plugin was updated under a live session whose shell had moved into another working folder, the reloaded tools looked for the board there, and every tool answered from an empty board while nine tickets were on disk. A board that reads empty now ends its summary and list with the folder it read. It is excluded locally through `.git/info/exclude`: the board is personal, and a team shares work through its tracker (a committed board broke four ways for a team: a pull replaced a colleague's board, two branches handed out one id, a stale exclude line split it, and it blocked branch switches). The write that first creates the board adds the line when git tracks no `.sidequest/` file and does not already ignore the folder, and that tool answer says so once. A tracked or already ignored folder is left as it is, and a failed exclude write never stops the board write. A write that creates the board in a folder outside any git repository says so once instead, in one line: where the board was created and that the folder is not a git repository. Nothing is refused. `scripts/boards.mjs` in the Sidequest plugin lists the boards this machine knows, read-only: the project folders the installed-plugins record names for Sidequest, the folders sessions ran in (the `cwd` in the head of a transcript under `<config dir>/projects/`, never the folder's lossy name) and any folders given as arguments. Each row has its open, done and parked ticket counts, when it last changed (the newest of the tickets' own `updated` days and log stamps, since a checkout or a sync resets file times; file times only for a board with no dated ticket) and whether the folder is inside a git repository (a walk up for `.git`, no process). A board nobody touched for a month is marked when it has no open ticket or sits outside a repository. Marked rows come first, then the ones outside a repository, then a count line. It removes a board folder only when told to with `--remove=<project folder>`. There is no registry of boards, no lock and nothing per tool call. A session inside a linked worktree resolves the board of the main checkout. A bare repository has no main checkout, and its common git folder is not a `.git` folder: when that folder's own `config` says `bare = true`, every worktree of it shares one board at `<common folder>/.sidequest`, read from that file with no extra process (a submodule or a separate git folder is not bare and keeps its working folder). Inside the common folder is the one place all the worktrees share and none of them lists, so the board needs no exclude line (git cannot list files there, so the exclude check already leaves it alone), and the prefix comes from the folder name without its `.git`: `uploads.git` gives `UPL`. Beside the folder would have named the prefix after whatever folder holds the repository.

```
.sidequest/
  board.json            id prefix, routing table, categories, settings, id counters
  tickets/SQ-12.md      one ticket per file
  stories/ST-3.md       destination, the short version (`## In short`), the analysis the person reads in the pane when one was written, the path through the code (`## Path`, a numbered `what (file:line) note` list) and the excerpts (`## Excerpts`, fenced under a `file:line` line) as data, the open questions under Decisions for you (numbered by the tool), decisions, out of scope, and a hand-over when a step before building asked for one
  briefs/SQ-12.md       the brief `start` last printed for that ticket, kept for its review, the story's proof and a wave
```

**Ids carry the board's own prefix.** Seen the week of 2026-11-16: every board gave out `SQ-<n>`, so in one conversation that spanned two projects SQ-4 meant two different things within an hour, and a team that commits its board gets the same id on two branches. So `board.json` holds `"prefix"` (one to ten letters, read in capitals): tickets are `<prefix>-12` and stories `<prefix>-S3`, the `S` keeping a story id from ever reading as a ticket id or a tracker key. The write that gives out a new board's first id (a board with no prefix, no ticket or story file and both counters at 1) picks it from the project folder's name: the initials of a name of several words (`photo-library` gives `PL`), else a short one-word name whole or the first three letters of a longer one (`payments` gives `PAY`), letters only. It never takes the prefix of a tracker key seen in the branch names (one `git for-each-ref` for local and remote branches, on that one write) or at the start of a title, in a branch or in an issue of that same call: the next candidate is taken (the name's own first letters, then its first letter with each later letter). That write's answer says which prefix it took, why any was passed over, and that `board.json` holds it, so a person can change it while there are few tickets; ids already given out stay, and still take writes and blockers. A board with a ticket or story on it and no prefix is from before prefixes: it stays on `SQ-12` and `ST-3`, is never given a prefix, and answers exactly as before. Everything that reads an id takes the board's prefix: the ticket ref that routes a spawn, the rule that a key shaped like a board id is not the tracker issue, the field repairs, the transcript rows (from the board read last) and the tool descriptions, which each session registers with its own board's examples (on a new board, the prefix its first write would take from the folder name and the checked-out branch).

**A ticket is the file named after its own id.** Seen on scratch boards on 2026-11-20: a sync tool's `SA-5.sync-conflict-<stamp>.md` and a file manager's `SA-5 (1).md` and `SA-5 - Copy.md` all carry `id: SA-5`, the id was listed four times, and a note loaded a copy and wrote it over the real `SA-5.md`. So only `<id>.md` is read as that ticket (the same in `stories/`). Any other file there is a stray: never listed and never written, and the summary and the list name it once with the id it claims. A file that cannot be read, or parses to no id or no status, is named as unreadable or damaged in the summary, the list, a ticket view of its id and a write that names it, and is never written. Every file name in the folder counts as taken for a new id, read or not: a create beside a locked `SA-5.md` took 5.

**Writes check the disk, with nothing stored.** The host's file interface has no exclusive create, rename or remove, and the write queue is per process. Seen the same day: two sessions creating at once on a new board took one id in 2 of 10 tries, both answered `created` and one ticket was gone; lines a person appended between a write's read and its write were gone 3 of 3 times. So every board write (the tools, the return record, the spawn line, a press on the pane, drop) reads the tickets it changes again right before writing them. One that changed since the read gets the whole call redone once on the new text; one that changed again by then is not written, and the answer says so and never names it as noted, moved or patched (seen: `noted PA-1.` followed by nothing was written to PA-1). A new ticket or story takes its number from a fresh look at the folder right before the write, goes to the next free number when the name is taken, and is read back after: when another session's file landed on the name, it is filed again under the next number and the answer says the id changed and why. `board.json` is written after the tickets, its counters the larger of what is on disk then and what this write has. A file that cannot be written is named in the answer with the reason. No lock, no lease, no registry.

**When board.json is lost.** With no usable prefix and tickets on disk, the prefix is the one most of their ids carry, and a board of `SQ-` tickets stays a board from before prefixes. A missing or empty `board.json` is written again by the next write that gives out an id, with that prefix and the counters from the files, and that answer says so. One that does not parse is left byte for byte: the first read and the first write of a session name it and say the defaults are in use until it is fixed (the summary and routing views name it on every read). Seen: a board of `SA-1` to `SA-5` with no `board.json` gave out `SQ-6`.

**A board that vanished.** `git clean -fdx` removes an excluded board and leaves the `.sidequest/` line it wrote in `.git/info/exclude`; the next read said `0 tickets in all` as if new. When the folder is gone and the line is there, the first board read of a session that finds it says a board was here, that it cannot be brought back from here, and that the next ticket starts a new board. Once a session, and nothing new is stored.

Every `start` keeps the brief in `briefs/<id>.md`, and a build ticket's answer names the file so the reviewer and whoever proves the story are pointed at it. Measured 2026-11-22 in real sessions on a scratch project with a story of eight decisions: a review prompt written by hand ran to 1,450 to 1,700 characters and carried 0, 0 and 1 of four decisions looked for, so 0 of 3 reviews spoke to the decisions; named the file, the prompt was 900 to 1,170 characters, the reviewer read the brief in 3 of 3 and all 3 reviews spoke to the decisions, at the same cost and time (about $0.50 and 75 to 86 s a session). **Analysis first.** For work that goes to the `plan` skill, reading needs no permission, so the first thing the person gets is what was found: what is asked in plain words and what each image shows, how it works today with `file:line`, what does not fit, then the first group of design questions. One board read opens it (the `planning` view: the settings, the stories and every ticket that is not done or dropped). A tracker issue is its description, its comments, the issues it links and every attachment: the tracker is asked for attachments even when the text mentions none, each image is opened, and one that cannot be opened is named and asked about. The long form (code excerpts with file and line, a text diagram of the path the change runs through, each option with where it lands) is written into the story as `## Analysis` before that message goes out, and the pane opens on it; a change in one place with nothing to choose gets a few lines and no long form. How it is proven and where it ends are lines in the playback that one word changes, the project's own step before building is a line there too, and they become decisions on the story, so a later session and land read them. A reported problem is made to fail first unless the request says to start another way. What the team would see (a tracker status, a branch, a commit) waits for its own yes. This replaced the course, which from 2026-11-23 to 0.30.2 was one short message agreeing how it starts, a written step, how it is proven and where it ends before any reading: in the second real run it landed before the person knew anything, so they could not judge it. Measured 2026-11-24 on a made-up service, top-tier model at high effort, a second model answering as a developer, to the first build. The first message with substance came after 170 to 242 s and $2.27 to $2.80 with a `go` in between under the course (6 sessions), and after 166 to 229 s and $1.75 to $2.10 with no stop before it (10 sessions), at 466 to 667 words with another 1,100 to 1,600 in the story. A mockup that changes the right answer was opened in 4 of 4 before and 6 of 6 after when the issue's text mentions it, and in 1 of 2 before and 4 of 4 after when nothing in the text does. Planning opened with one board read in 15 of 15 (2 or 3 reads before). A bug report was made to fail first in 2 of 2 and reached its build in 3 turns (4 or 5 before). A trivial issue reached its build in 2 turns and 58 s with no story before the yes, and a small exact request was edited after 13 s. No tracker move, branch or commit came before a yes in 10 of 10. Not measured: the mid model, a person, the story view in a terminal. In the first real run on it a session read earlier sessions for prior work for five minutes: that is wanted, and limits on it that 0.31.1 added were taken out in 0.31.2. **Board rows are for the person.** A board read's row names no view (`board read`, or `board read SQ-2`), and under it is one line of what is open (`3 open tickets, 1 waits on you`), as it stood when that read ran, and none at all when it is the line the board read before it drew: a session polling the board drew nine identical rows in a row on 2026-11-24. The host gives a row no view of the row before it, so the board's own `tool.call` hook notes each read's line in order and the `ToolResult` hook draws an empty Box for a repeat; the `ToolUse` row stays, so the call is still seen in place of the text the model read; expanded, the host shows all of it. Tested in mounts, not seen in a terminal.

`settings.beforeBuilding` is optional: `{ "label", "how", "readBack" }`, one step a project does between agreeing work and building it, in its own words. `label` is the team's name for it (a plan of action, a design note), `how` is a skill of the project or a line or two of plain instruction, `readBack` says how to read the result back when the person says go. The board knows nothing else about the step: no template, no sections, no status, no document tool. The `routing` view prints it as one line only when it is set, and the playback offers it by its label, as a line one word changes. Chosen, it is done once the plan is agreed, in the conversation with the person, never by a worker or a scout and never in the background. The `plan` skill first writes the hand-over into the story file as the section `## Hand-over` (story field `handOver`) under six fixed headings, `Goal`, `Needs first`, `Risks`, `Slices`, `Open questions`, `Links`, each present and `none` when empty: that is the contract a project's skill is written against, and it reads it from `.sidequest/stories/<id>.md`. It then does what `how` says, records the address the step gives back as a decision on the story (worded so nobody building changes the result), and holds the work with a checkpoint the board already has: a `hitl` review ticket titled `<Label> in review: <address>` that every build ticket is blocked by, so the waiting view names it with no new state. On the person's go it follows `readBack`; the result as it then reads wins over the tickets. What differs is put to the person before any ticket changes, a difference their go already settled is applied and said, and only then does anything run. With no `readBack` it runs from the tickets as they are. `local only` is the story file itself, named in one line, with no hold. Measured in real sessions on a scratch project, once with a plain instruction that writes a file from a template in the repository and once with a small skill of the project: the choice showed with the team's label in 4 of 4, the file appeared in the project's own headings, nothing started and the waiting view named it in 4 of 4. After the written result was edited by hand (a slice dropped, an open question answered the other way): on an earlier wording 1 of 2 sessions built the dropped slice anyway; on the wording that shipped, the session whose go left the difference open stopped and asked, and the one whose go settled it changed the ticket first, 2 of 2, and in both the board matched the edited result before the first agent started. Handed over, the project's step is never picked, since it needs a person and would hold the build for one (seen: the handed-over run in a project with the step skipped it and said so). A hand-over line that starts with two hashes is pushed one level down when the story is written, and a hand-over's own heading is taken off: a break attempt on 2026-11-23 showed such a line reading back as another section and the rest gone after the next write. A `readBack` of the wrong type is named among the board.json problems, where it was dropped without a word. Writing to a place outside the repository is tested, not seen working. There is no observed failure behind the setting, which `SCOPE.md` asks of a new one: it is here on the person's word, from how a team reviews written work before building.

**Tickets are agreed with the person.** The playback lists each proposed ticket as a short block: title, what it touches, what it waits for, and its `Done when` as a check a person can read and judge. They can retitle, drop, add or reword, and `go` takes the list as shown. That was largely so already (the pushed version listed tickets with checks a person can judge in 2 of 2 playbacks); new is that a check the person worded is filed as they said it, the line starting `In the person's words:`, and the brief puts one sentence under such a `Done when`: it is met exactly as written, and when it cannot be, the worker stops and says so in `needs`. In a real session the reworded check was filed without the marker and with an example added until the `doneWhen` field's own text asked for it; with that, it was filed as said. The tickets are filed at the playback, under a story patched `awaitsYes: true`, and stay proposed until the yes: no new status, the mark on the story says it. The frontier and `start` never start one (start's refusal says `its plan still waits for the person's yes`, also when a session forgot to clear the mark, with how to clear it); the summary, the band, `now`, `planning` and the pane's Next leave them out of open work and name them as proposed; `list` marks them. The yes is the patch `awaitsYes: false`, which makes them live; `stop` with the story parks them and clears the mark. Observed in full runs: the playback was read twice, in the chat and on the board, and the person asked for one place to read and decide.

**Nothing outward names the board.** The board is personal and operational. A branch name, a commit or merge message, pull request text, a tracker comment, a committed file and whatever a step before building writes speak of the work in the project's terms: the tracker key where there is one, the behaviour that changed, how it was checked. Never a board id, the board, this tool or its words. The rule is stated in every brief, beside the board id it is about (`## What leaves this machine`), and once for the landing session in the land page; the worker's page and the land step that said the opposite are changed. Measured on full runs to landing, grepping branch names, every commit message and the pull request draft for the board's prefix, the tool's name and its words: before, 4 commit-message lines and 2 draft lines with no tracker key, 2 and 1 with one; with the rule only in the worker's page a worker with no tracker key still began 2 of 2 commit subjects with the board id; with the rule in the brief, 0 hits in 4 of 4 runs.

`settings.checks` is optional free text, a few lines: what the checks need, where they can run, the command that works. Every brief carries it as its own section and the `routing` view prints it or says it is not written down (observed 2026-11-22: a worker spent 18 minutes finding out how the tests run, and the next two took 3 minutes each once that was written into their tickets by hand). `settings.shared` is optional: an object of name to `{ "what": "<one plain line>", "refresh": "auto" | "ask" | "<command>" }` for what exists once in the project (a running stack, a database, a port) and how the running thing picks up new code. A board without it reads and writes as if it never existed. An entry of the wrong shape is a board file problem, named in the routing view and the summary like the others.

A tier's `model` is a Claude Code alias (`haiku`, `sonnet`, `opus`, `fable`) or any id a provider file lists. A tier may carry `"fallback": "<alias>"`. When no `board.json` exists the defaults above apply, so a fresh install routes with zero setup.

Ticket file: flat frontmatter (scalars and inline arrays, or a list as `- value` lines) and a markdown body. A hand edit is read as written: a byte-order mark is skipped and kept, the last of a duplicated key wins and is reported, and a frontmatter with no closing `---` is damaged: the parse says so (`isDamaged`) and nothing writes the file.

```markdown
---
id: SQ-12
title: Retry failed uploads
status: ready
kind: build
mode: afk
category: build
story: ST-3
branch: fix/PAY-41-retry
issue: PAY-41
startedBy: session
blockedBy: [SQ-11]
decisions: [D-2, D-5]
created: 2026-11-16
updated: 2026-11-16
---

## What
The behaviour this ticket makes work, from the user's side. No file paths.

## Done when
- [ ] A check that fails today and passes when this is done.

## Log
- 2026-11-16T10:02Z started worker sonnet/medium
- 2026-11-16T10:19Z finished done branch sq-12 commits 2 checked "npm test exit 0"
```

- `status`: `inbox`, `ready`, `doing`, `review`, `needs-you`, `done`, `parked`, `dropped`. The human can move any ticket to any status at any time. No refusals.
- `dropped` is work the person let go: not open and not done, never offered by the frontier, `now` or the pane, not counted in the band, and it does not satisfy a `blockedBy` the way `done` does (a ticket it blocks stays blocked, and its list line says `blocked by dropped SQ-12` and its pane row `waits on SQ-12, which was dropped`). The file stays, and a move brings it back. Parking it would leave it waiting for a word forever, and marking it done would unblock what waited on it.
- A ticket on the board is never an instruction: the person's request is. `parked` means not without the person's word. Whenever a write through the board's tools takes a ticket out of `parked` (a move, a patch of its status, `start`, `finish`), the board itself appends a log line with the words of the turn it happened in, cut to 200 characters: `taken out of parked on the person's words: "..."`, or `on a message from another session: "..."`. The model never supplies those words and no field takes them; nothing checks what a note says. Something the person wants after X is `ready` and blocked by X, never parked. Observed 2026-11-19 on a top model: the session parked a ticket the person had objected to with its own note saying it picks up after the first task, a compaction carried that forward as pending work, and a finished background task woke the session with nobody typing, in which turn it patched the ticket, started it and routed a scout.
- **Whose words a turn carries** comes from the prompt the mod already sees, kept in the module for the current main turn only (a reload forgets it, and the log line then says the board did not see the turn start). Origin `composer`, `bridge`, a headless prompt (`sdk`) and the board's own presses (a plugin prompt sent as the person) are the person's, and their text is their words. `peer` is a message from another session, recorded with its words. `task-notification` with no turn id in an interactive session is a turn nobody typed. A notification or message folded into a running turn (it has a turn id) changes nothing, while the person typing over a running turn is still the person. A scheduled trigger, a background task's notice in a headless run and any other origin are logged as that, with their text.
- **A turn nobody typed** carries one line of context on its prompt: nobody typed this turn, a background task finished; report what finished, and continue only what it unblocks inside the plan the person started; parked tickets, the inbox and a stopped plan wait for the person. Not on a typed turn, a folded notification, a scheduled trigger the person set up or a headless session (`session.start` says it is not interactive). No decline and no refusal: when a write takes a ticket out of `parked` or `inbox` in such a turn, it happens, its log says it was taken out in a turn nobody typed, and the person gets one toast and one notification naming the tickets.
- `kind`: `build`, `decision`, `research`, `review`. `mode`: `afk` (an agent can finish it alone) or `hitl` (needs the human; never dispatched).
- The **frontier** is every `ready` ticket in `afk` mode whose `blockedBy` tickets are all `done`, or in `review` with a pass or a skipped review as the last review note when `settings.worktrees` is false: every run commits in the one checkout, so its work is already where the next ticket will work. With worktrees on a blocker has to be `done`, because its commits sit on its worker's branch until land (a first version also counted two tickets with the same branch field, which is nearly every pair made in one checkout; a read-only review caught it before it shipped). Observed 2026-11-22 in a real four-ticket story on one checkout: a ticket only becomes `done` in land, land runs when nothing is left to start, so a blocker that had passed review kept the next ticket off the frontier for good.
- `uses` lists the names from `settings.shared` a ticket holds for its whole run; absent when it uses nothing shared. A name the board file does not know is written and named in the reply, and is held all the same. With `settings.worktrees` false, every ticket whose category runs on the worker role also uses `checkout`, written nowhere: two workers in one checkout mixed each other's work and both claimed a verify that proved neither (2026-11-19 baseline).
- A thing is **held** by any ticket that is `doing` and uses it. Nothing else: no file, no timestamp, no lease. A hold from outside the board is such a ticket (`hitl`, `doing`, using the thing), created when the person says the thing is busy and moved to `done` when they say it is free. The frontier view marks a ticket whose thing is held: what it waits for and which ticket has it.
- The pane and the band read the same board. The pane's cards and the counts the band draws are two pieces of state, and every refresh of the cards now publishes the counts from the same tickets; a read of the board by the session refreshes both too. Seen on an earlier version in a real session and reproduced in a test that failed before the change: a waiting ticket was parked by a change made outside the session, opening the pane re-read the board and showed it parked, and the band went on saying `1 ticket needs you`, because only the session's own writes republished its counts. With no action in the session neither view changes: there is no timer, no watcher and no read per turn.
- When the pane's tickets span more than one piece of work it groups: what runs this moment stays on top, then one block per piece in the shared order, headed by the piece's handle and the branch its tickets share, each ticket a row that begins with what it is (`waits on you`, `from earlier work`, `interrupted`, `next`, `done`) and ends with the board id. Built work in `review` sits under its own **Being checked** label after Now, as it does in the layout by status. The wide band then names the pieces that need the person (`2 tickets need you: PAY-41, PAY-57`, up to three, then `and N more`). With one piece of work the pane and the band are what they were, apart from the handle's order. Measured on 2026-11-23 on a scratch board with two keyed stories of three tickets each and one story with no key: before, every row led with the board id, the pieces of work alternated inside each status section and the story with no key showed only ticket titles; after, each view printed one heading per piece. A board with one story printed the same pane before and after except for the handle. The band was drawn in tests only. A read-only break attempt before the push made four things happen, all fixed: the note pasted when a write makes a ticket wait numbered its block by the old board-wide order, so an answer taken from the note could land on another ticket than the grouped view's (the note now numbers and names as the view would); the band counted a waiting ticket of no piece without naming it (it is named `other tickets`); a heading could be blank, carry a key twice or be a raw story id; and a board read that came back with no tickets, as a listing that fails for a moment does, would have blanked both views (it now repaints nothing).
- The pane and the band keep quiet about older work. A needs-you ticket this session never touched and that was last touched a day or more ago is from earlier work: the band's warning and the narrow band leave it out, the wide band counts it as `1 waiting on you from earlier sessions`, and the pane lists it under its own dim label. The pane's Done section lists only done tickets this session touched. The published summary keeps `needsYou` as every needs-you ticket and adds `needsYouFromEarlierWork`. The waiting view a session reads calls a question earlier work by the same rule (it used a week), still only when the session has waiting work of its own. Seen 2026-11-23 on an earlier version in a real team repository, and still so in the code before this change: a person working on one thing saw three done tickets and a four-day-old question from another piece of work and read the whole pane as being about the wrong task. Not looked at in a real pane; whether a done ticket's branch still exists is not asked.
- `branch` is the branch the ticket's work is on: the one checked out when the ticket was created, read from the checkout's `HEAD` file (no process), then the branch `finish` was given, when a local branch of that name exists (one git process, only for such a value) and it is not a host-named `worktree-agent-*`, which is temporary and leaves the field alone. `start` never merges it: a worker in a worktree is told to merge the branch checked out in the main checkout at start, and only where the repository has a remote, because without one the host cuts the worktree from what is checked out. Observed 2026-11-22 in real sessions on a scratch project: a ticket whose `branch` was set to the name its work should land on got a brief that opened with a merge of a branch that did not exist, and the worker stopped with no commit; left alone, the closing view named the branch the ticket was filed on after the work sat on another. The fork-point facts compare a run against the checked-out branch when the ticket's branch is the run's own, a drop keeps such a branch and says so, and the line about tickets on another branch than the checkout leaves such a ticket out. `issue` is a tracker key (capital letters, a dash, digits) taken from the start of the title, else from the branch name; one shaped like this board's ticket ids is not taken. Both can be given and patched, and a hand edit survives, since they are only derived on create. Seen in a team repository: a bug's ticket and its branch drifted apart once the checkout moved to another task, and a board id meant nothing beside the tracker key and branch the person thinks in.
- `pullRequest` is the address of the pull request that carries the ticket's work, or only its number (`#130`). `land` sets it when it opens one; create and patch take it like any field. Nothing derives it.
- `startedBy: session` marks work the session opened on its own; absent means the person asked. Seen in real use: a session opened work nobody had asked for yet and the person lost track of their current task.
- Wherever the board names a ticket (list and frontier lines, the ticket view, the waiting view's handle, the pane's rows and detail) the tracker key leads, and the branch, the pull request number and "started by the session" follow the id when the ticket has them: `PAY-41 SQ-12 (branch fix/PAY-41-retry, pull request #130)`. The person knows the work by the key; the board id stays behind as the small handle.
- A **piece of work** is a story; tickets with no story but one tracker key are one piece (and join a story whose tickets or title carry that key); a ticket with neither belongs to none. Its handle is its tracker key and the story's title without the key repeated, else the story's title. The waiting, now and closing views group by piece only when the tickets they show span more than one: a heading per piece (its handle, and the branch its tickets share), each ticket under it as its title without the key and its id in brackets, a branch only where it differs from the heading's, and tickets of no piece last under `Other tickets`. Pieces holding a ticket this session touched come first, then the work on the checked-out branch, then the rest by their lowest ticket id. Waiting keeps one numbering across the view, so `1A` answers the first block; closing's count line names each other piece with its counts. One piece, or only loose tickets, reads as before. Measured 2026-11-23 on a scratch board with two keyed stories of three tickets each and one story with no key: every line led with the board id, the views listed by status or id so the pieces alternated, and the work with no key was told apart only by ticket titles.
- A ticket that **waits on the person** (`needs-you`, or `hitl` and neither `done` nor `parked`) carries a `## For you` section first in its body: `Question:`, `Why now:`, `Options:` with one `- <label>: <what you get>. Costs: <what it costs>.` per option, `Recommended:`, `If you never answer:`, and `Steps:` (what to open and what to look for) for a task with no decision in it. It is written for someone who was not in the room, answerable from a phone: no ticket ids, internal names or words the project invented. Before a commit, a push or a pull request that waits on the person it also holds what they say yes to (`sayingYesTo`), filled in two steps: `What changed:`, `How it was checked:` and `The hunks that carry the design:` once the proof has run; `What the review found:`, `Commit message:`, `Pull request title:` and `Pull request description:` when the review is back. Each is its name on a line and its text under it indented four spaces, so blank lines, a diff's leading spaces, a `## ` heading in a description and a line that looks like another part's name all read back as written. The ticket view draws them (the hunks as a diff, the outgoing words as written) above the question with `The review still runs.` until the second step. Once the review is back the view leads with two or three summary lines (the review's outcome from the ticket's log and the ticket's branch, topped up with the first lines of what is said yes to; never a size counted from the hunks, which are a chosen part of the diff: observed on a real board, that count read 4 files where the session's own text said 10), the question, its answers, the extras, the words field and Send, and the parts follow under `What you are saying yes to`. Observed in a full run: the question and Send came after 43 lines of diff, the review and the words that go out, in a pane that shows about 45 rows. The session sends the stored words; a patch that changes them on a ticket past the yes (out of `needs-you` after being in it) logs `words changed after the yes: <part> from "..." to "..."`, and `closing` names it. The waiting block's last line names the branch the ticket carries and never the one that happens to be checked out; when the change is brought to the person's checkout on the ticket's branch, the land page patches `branch` to it. Observed in a full run: the line said `branch main` while the change sat on the ticket's own branch in the checkout. Only a decision that cannot be undone, spends money or reaches outside the project, or is taste or product direction only the person has reaches them. Any other choice with a recommended answer is taken by the session, which notes what it chose and how to undo it. A hand-written section is kept as written by any write that does not change it.
- A ticket's brief carries the story decisions the ticket names in `decisions`, in the story's order, and no others. A ticket that names none gets all of them. Seen 2026-11-19: a ticket naming 4 decisions got all 18 of its story's, about 1,900 words, and the `start` answer prints the brief.
- A story file holds the destination, the decisions (`D-1 ...` with question, answer, who decided: `human` or `default`, and the day it was made, the UTC day; a decision the person took also keeps their own words, `Their words: "..."`, cut at 200 characters: the length of two short sentences, enough for an answer and its reason and short enough to sit on one line of a page. A default keeps the day and no words. A question decided again is a new line with its own number and day, and the earlier line stays. A line with no day, as older boards wrote them, reads with no day and no words. The cut counts what a person sees as one character, so a flag, a joined emoji or an accented letter at the cut is kept whole or left out. The ticket tool's `decisions` take `words`, and the answer pressed on a plan's decisions is stored in the story as `decisionDaySent` and `decisionWordsSent`, the words as typed and uncut until the session writes them as a decision, where the cut applies. Where a team tracks its board in git, the words go into its commits), what is out of scope, and nothing else.

### Routing

Routing is a property of every spawn, with or without a ticket.

- A spawn is **routed** when its prompt starts with a ticket ref in the board's prefix (`SQ-12`, or `Ticket SQ-12:` as the brief writes it), or its prompt or description carries a route tag (`[route:hard]`). A ref further into the prompt is a mention and routes nothing, and so is a tag: it counts at the start of the prompt, straight after the leading ref, or in the description, never further in (observed 2026-11-20: a brief whose What quoted `[route:review]` was routed as review). A tag names the category directly. A ref alone uses the ticket's category. Both together: the tag decides the route and the ticket gets the record.
- A spawn is **unrouted fan-out** when it carries no tag, names no model, and would silently inherit the session model: a workflow agent whose script names no agent type, a `general-purpose` agent, a Sidequest role. Those run on the category named by `settings.unrouted` (default `build`). Set it to `inherit` to switch this off. This is the rule that stops forty readers from running on the most expensive model because nobody said otherwise.
- Left alone, always: a spawn whose call names a model (the orchestrator chose), an agent whose own definition names a model or an effort, and forks. The hook can't read an agent's definition, so only types known to name neither get a model and effort: the engine-provided `general-purpose`, `Explore` and `Plan` (a spawn's `provider` is `engine`), a teammate or workflow agent with no type (`teammate`, `workflow-subagent`), and `sidequest:*`. Any other type carrying a tag or a ref keeps what its definition says, and is still recorded: `requested none`, effort `own`, the model it resolved to, on the ticket log too when it carries a ref. We never deny a spawn.
- `agent.spawn` hook: resolves category to tier and sets `model`. It fires for workflow agents too, so a Workflow script routes by starting each agent prompt with a route tag and naming no model.
- Effort: the board never changes an `Agent` call's input. In auto mode the classifier reviews the call as the model wrote it, and a call a hook changed after that review is refused: on 2026-11-18, while a `tool.call` hook still added the tier `effort`, 5 of 6 routed agents in auto mode never started ("Not run · auto mode's check had no usable answer", the transcript naming the changed input), and 1 of 1 ran in default mode. So the `agent.spawn` hook remembers the tier effort for every agent it routed whose call named none, and a `turn.step` hook applies it to each of that agent's model requests, the same way for an Agent call's agent and a workflow's. That handler does one map lookup, and for the main session one count for the pane's own-work row, and nothing else, because it runs on every model request. `agent.spawn` never sees a call's effort, so the `tool.call` hook on `Agent` only notes, by the call's id, that it named one, and hands the call on as it came. A workflow agent whose script names a model is taken to have named its effort too. With `CLAUDE_CODE_EFFORT_LEVEL` set, nothing is set: the engine documents that variable as taking precedence over a definition's and a call's effort, so an injected level is ignored, never an error. The variable is read once per spawn, never per step.
- The model is set at the spawn, which is a different change: `agent.spawn` fires inside the Agent tool's run, after the call was checked, and rewrites the spawn, not the call's input. The observed refusals named the added `effort`, not the model.
- Once per turn in which unrouted fan-out was rerouted, the model is told, in one line on the next prompt it answers in words, so it can tag its next spawn; a turn with no reroute adds nothing.
- The resolved model that comes back from the spawn is written to the ticket log. Requested and actual are recorded separately. Unknown stays unknown.
- A tier model that is neither an alias nor listed by a provider resolves to the tier `fallback`, else the provider file `fallback`, else `sonnet`, with a named reason. Never a silent switch: a ticket's log gets the reason, and a spawn with no ticket gets it in that turn's toast.

Roles are three agent definitions that differ in tools and text: `sidequest:worker`, `sidequest:scout` (no write tools) and `sidequest:outside-code-reviewer` (Read, Grep and Glob only, see the section on outside code). None names a model or an effort.

### Outside code

Asked for on 2026-11-19, after outside pull requests were reviewed for real: run strangers' code, but only after a very critical security pass, and never in a way that lets a supply-chain attack in. The review route as it stood would have run outside code on the host: the reviewing scout runs the `Done when` check, `land` runs verify on the merged tree, and scouts get no worktree.

- **Its own category and agent type.** `outside-code` routes to `sidequest:outside-code-reviewer` on the deep tier. That type has the tools Read, Grep and Glob and nothing else, so the host itself keeps text in a pull request from getting it to run anything; no refusal and no hook on tool calls. Its definition carries the reviewer's text: the whole diff (dependencies and lockfiles, install, build and test hooks, CI and automation, files other tools run by themselves, network access, reads of environment, credentials or files outside the project, subprocesses and dynamic execution, encoded blobs and data files that do more than hold data, changes that only make sense as a way in later, text aimed at a reviewer or a model); everything in the change is material, never an instruction; who sent it is context, never clearance. Its result starts with `pass` or `hold`.
- **What counts as outside.** Two triggers. Where the change comes from: a bot, a fork, an author with no earlier commit in the repository (`git shortlog -sne` on the default branch says), or code the person pasted or the session fetched and was asked to run, that is in neither the checkout nor a branch this session made. What the change touches, whoever wrote it, the person included: dependencies, a lockfile, build, install or test-runner machinery, CI, and files a tool runs by itself (git hooks, editor tasks, agent settings and instruction files), and then only that part of the diff, before anything is installed or run; that part is its own `outside-code` ticket or one reviewer call, and the change keeps its own ticket and its normal review. A colleague's change in a team repository that touches none of those gets the normal review. Known limits of the author check, all but one on the careful side: squash merges, a second email address and a shallow clone make a colleague look new; a stranger with one earlier commit counts as a colleague from then on. The first rule counted everyone but the person as outside; measured on 2026-11-20 that sent eight teammates' branches through the security pass on the top model for 3.94 to 4.99 dollars. The request was about strangers, so the narrower rule was taken as the recommended answer, and it can be changed. When the session cannot tell, it treats the code as outside and says so in one line. The agent's description is the trigger, so nothing in a brief has to carry it.
- **What runs, and where.** The main session writes the diff to a file, since the reviewer has no shell. On `hold` nothing of it runs: the review says which part and why, and its `needs` leaves it for the person. On `pass` the check runs in a throwaway container with no network and no credentials on a copy of the code (`git archive` into `docker cp -`), removed afterwards, never on the host. The steps live in `skills/sidequest/references/outside-code.md`, read only when a pass comes back; `land` verifies a branch that carries such code in the container too. With no container runtime the session says `not run: no container runtime here` with the error and runs nothing on the host. It removes the containers and temporary refs it made and names anything it could not.
- **What a ticket about the project's own code pays.** Nothing per ticket: no brief words, no tool calls, no stops. The standing cost is the agent's description in the session's agent list (under 60 words) and one more name in the category list.

### Finished worktrees

Observed 2026-11-18 in a repository after weeks of use: worktrees beside the main checkout, loose sibling folders from a plain `git worktree add`, a few under the agent worktree folder and one in another project's temp folder, about a third of them safe to remove. `land` only removes the worktrees the board made, so it touched none.

- `scripts/worktrees.mjs`, run on demand only, gives every linked worktree of the repository a verdict, wherever it lives and whoever made it: path, branch, uncommitted or untracked files, commits on no remote and not merged into the main checkout's branch, locked, last commit date. `safe` only when nothing is uncommitted, nothing is only there and it is not locked; anything else is `keep` with the reason in plain words. Only there covers ignored files too (seen on a scratch repository: a worktree holding an ignored `.env` read safe and went with it): `git status --porcelain --ignored` lists them, a wholly ignored folder as one entry, and an ignored file counts as only there unless the main checkout holds the same bytes at the same path, an ignored folder unless the main checkout has that folder too. Measured on node, python and rust scratch projects, worktrees that ran the project's own install, build and tests read safe and every lost-file case read keep; an install that ran only in the worktree, or a cache in a new package folder the main checkout has not built yet, reads keep. The reason names up to three paths and counts the rest. A table by default, JSON with `--json`.
- `--branch=<name>`, given once or more, narrows the report and any removal to the linked worktrees on those branches and those branches themselves, whatever their names; `--worktree=<path>`, also repeatable, narrows to the worktrees at those paths. The main checkout's branch is never a candidate. `drop` uses `--branch=`, so the board never writes a verdict of its own, and `land` uses both for the tickets it landed and its own landing worktree (seen on a scratch repository: land's unnarrowed run removed a person's clean hand-made checkout with its branch).
- `--remove-safe` removes exactly the safe ones with a plain `git worktree remove` (never forced) and deletes a branch only when `git branch -d` accepts it. Before that, each junction or symbolic link directly inside the folder that leads into the main checkout is unlinked, never followed: on Windows `git worktree remove` deletes the files behind a directory junction (seen 2026-11-18 with git for Windows), and a junction needs no special rights to make.
- It deletes a branch only when another local branch or a remote-tracking ref holds its tip and `git branch -d` accepts it, never forced, and says `no other branch or remote holds its commits` when none does. A worktree with a rebase, merge, cherry-pick, revert or bisect in progress is `keep` in every mode (a break attempt on 2026-11-22 removed a named worktree in the middle of a rebase and lost the plan). Observed 2026-11-22 on a scratch repository: with the main checkout detached at the run branch for the verify, land's cleanup of that branch removed the worktree and deleted the branch, because git counts a detached checkout as holding it; after the next checkout the commit was on no branch. A worktree named with `--branch=` or `--worktree=` holds no commit of its own when it is on a branch (the branch stays) or detached at a commit a branch holds, so it goes while the branch is kept: before that, land's one command removed nothing in 5 of 5 real runs where the branch stayed open for a pull request. When the removed folder is `agent-<id>` and its branch is another, the host's leftover `worktree-agent-<id>` goes under the same rule. A run with neither flag judges as before.
- It also looks at what an older version left behind, which no linked worktree shows. Local `worktree-agent-*` branches with no worktree get the same verdict words: `safe` when fully merged into the main checkout's branch or with no commits of their own, `keep` with the commit count otherwise. Given a root folder as an argument, it lists the folders one or two levels under it whose `.git` file points into this repository's worktree administration but which git no longer has registered: `safe` when every file in the folder matches an object the repository already holds, `keep` with the reason otherwise (a file git has no copy of, a link, a folder it could not read). Safe branches print as one count line with the keeps named, never one line each. A safe linked worktree whose folder or branch is not agent-named (a person chose the name) is named in one line after the summary, which tidy shows before removing; seen on a real run, a sibling folder with a chosen name went with the agents' ones without being named. Agent-named safe ones stay a count. A `--remove-safe` with no narrowing leaves the person-named ones and says so, `--named` removes them too, and a narrowed run removes what it names: naming it is asking for it. `--remove-safe` deletes the safe branches with `git branch -d` and removes the safe folders, and touches no keep. `--only-under-root` narrows the linked worktrees judged and removed to those under the root folder, while the branch verdicts still read every linked worktree: the upgrade's home cleanup uses it, so a session's own worktrees elsewhere are never touched, and the JSON answer then carries `isOnlyUnderRoot: true` so the caller can tell it from an older copy. Nothing here runs unless asked.
- The `tidy` skill runs it, shows the table, says in one line what can go and what stays, and removes the safe ones on the human's yes, or at once when they asked for the cleanup. It never touches one marked keep.

### When a run dies without a result

A session can end mid-run (a crash, a spend limit, a closed window, the person pressing stop), and nobody is left to call `finish`. Nothing has to notice at that moment, because the board file already says `doing` and the log says what was started. Observed 2026-11-19: the person interrupted a session in the middle of its work, started another and asked it for something else, and nothing told the old work from live work, so the new session picked up a ticket from the board and ran it.

- **Interrupted is a label, never a requeue.** A `doing` or `review` ticket with no live run in this session reads `interrupted` wherever the board names it: the summary (one line naming each, saying it is earlier work and not a request, that resuming, setting it aside or dropping it is the person's word, and what a typed continue or go on means: resume, while this conversation has written to no ticket of its own (in a real run a session that read the line without that asked which), and the line says that condition itself, because it stays in the conversation after the moment it was read: a session that read it before it had work resumed an old ticket two turns later, on a go on about the ticket it had just built, and the work already in hand once it has (in a real run a go on about the ticket in hand was read as the word to resume an old one), the list, the `now` view and the pane. The status on file does not change and nothing is written. Not interrupted: a ticket whose agent this session has alive (it reads as running), a ticket this session started, created or finished whose run was not cut off (a `review` ticket waiting for this session's review reads as today), and a `doing` ticket whose return nobody recorded (that has its own label). Which agents and tickets are this session's is the spawn record in `$.state` plus the tickets this session wrote through the tools, kept in the module.
- **Honest about what it cannot know.** Beside the label, what is known at the moment of looking: when the files of the ticket's worktree last changed (`files changed 40s ago`) and when its agent's transcript last changed (`last activity 3h ago`), or only `no run in this session` when neither is found. The agent id comes from the log's spawn line; the worktree is found through git's own folder for it (`worktrees/agent-<id>/gitdir`) and walked to at most 60 folders; the transcript is looked for under the last five sessions of the project in the host's transcript folder. No process, no lease, no heartbeat, no timer, nothing stored. Looked up only when a board view is asked for or the pane's cards are rebuilt for another reason (a board write, session start, `/board`), never per tool call. A board with nothing interrupted costs two state reads and looks up nothing.
- **Resuming says what changed since.** `start` on an interrupted ticket runs git in the main checkout and the brief gets a `What changed since` section with only the lines that are true: the commits already on the run's branch, oldest first (the branch from the log's result lines, else `worktree-agent-<id>`), to merge and build on; uncommitted files in its worktree when it still exists; files the branch touched that changed on the base since (the ticket's `branch`, else the checked-out one); a last commit by someone other than the checkout's git user; a branch that moved on the remote, with never a force push; and, first, a branch that is already an ancestor of the base (`git merge-base --is-ancestor`, in the same start), named and called already merged, so the run checks the `Done when` there before building it again (seen 2026-11-20: a doing ticket whose branch was merged was started again with nothing said). Nothing is fetched. Starting a ticket that is not interrupted runs no process and its brief is unchanged.
- The band never calls such a ticket running. `doing` with no agent alive in this session reads `1 doing, no agent running`.
- A decision the human gave mid-run is recorded on the ticket or the story when it is given, never held only in the conversation.

No marker written at the moment of death, no heartbeat, no lease. A session that died cannot write one, and one that could would be the lease machine the older Toolshed had.

### Leftovers that really conflict

Leftover tickets show to the person on the pane. The model hears about one only for a real conflict, only inside an answer `finish`, `ticket` or `start` already gives, and never as a reason to stop: a line that cheap models read as stop and ask has failed.

- **The same files.** When `finish` records a ticket, its files are the `changedFiles` it was given, else the `changed` line the board logged when the agent returned, else the diff of its branch (the `branch` given, else the run's). Every other open ticket (not `done`) whose run branch, else its own `branch`, is neither the base nor this ticket's branch has that branch diffed against the base with three dots, so a merged branch changes nothing. The base is the ticket's `branch`, else the checked-out one. A file in both counts unless it is a common lockfile (`package-lock.json`, `yarn.lock`, `Cargo.lock`, `go.sum` and the like), marked `linguist-generated` in the repository's attributes (left out by the diff itself), or ignored (`git check-ignore`, run once, only when a file is left). The line names the other ticket's handle, at most two files and then a count, and its branch, which is not merged yet.
- **The same tracker key.** When `ticket` creates a ticket or `start` starts one, another open ticket with the same `issue` gets a line naming it. Tickets made in the same call and tickets of the same story do not count: they are one plan.
- **The line** is one fact followed by `carry on unless they really conflict`. It names two tickets at most and counts the rest. Each pair of tickets is said once per session, kept in the module, so a reload may say it once more. It is never a question, a refusal or a status change, and nothing is written to either ticket. It never appears for small inline work, which has no ticket.
- **Cost.** Git runs only inside that `finish`, only when another open ticket has a branch and this one changed files: one read-only `git diff` per such ticket, never a fetch. A board where no other open ticket has a branch or a shared key gives the same answers as before and starts no process.

### For a team

The first real session ran in a team repository where work lived on branches and pull requests the board knew nothing about. So a ticket knows its pull request (the `pullRequest` field), and the board asks the remote and the tracker's command line (`gh`, the one `land` delivers through) about it, but only when the person looks at a view or a ticket starts. Nothing here runs per tool call, at session start or while idle, and nothing is ever written to a ticket.

- **Only for team work.** A lookup is made only for a ticket with a tracker key or a pull request, and only in a repository with a remote, read from the git config file (no process). A ticket with neither starts no process in `start`, `finish` or any view, and a project with no remote reads exactly as before.
- **Short and fail-open.** Every lookup has a 3 second timeout, and the lookups of one view run side by side, so together they take no longer than one. A view asks about at most 8 tickets, newest first. No tracker command line, not signed in, offline or slow: that line is left out and the view reads as before.
- **Where each pull request stands.** The `waiting` view asks the tracker once per ticket (`gh pr view` on its `pullRequest`, else on its branch when the checkout knows that branch on the remote and it is not the remote's default) for open tickets and for `done` tickets with a pull request; parked ones are left alone. A ticket whose open pull request has changes requested or failing checks comes back under what waits on the person as a numbered block after the written ones, even when it is `done`: it landed and came back. A ticket already waiting keeps its own question. The rest are one line each under `Where the pull requests stand:`: a conflict with its base, or `approved`, which asks nothing. A merged or closed pull request says nothing.
- **Someone already on it.** `start` on a ticket with a tracker key makes one tracker lookup for open pull requests by anyone but the signed-in person that carry the key, and reads the remote branches the checkout already has (never a fetch) for one carrying the key that someone other than the checkout's git user committed to last. The ticket's own pull request and branch do not count, and a branch that carries one of those pull requests is said once, as the pull request. One line names who and where, two at most and a count, and the ticket is started all the same: a fact for the session to pass on, never a refusal.
- **No resume offer on someone else's branch.** The `summary` and `now` views ask git who last committed to an interrupted team ticket's run branch (`git log -1`). When it is not the checkout's git user, that ticket leaves the interrupted line and its own line says whose work it is now and that it is not offered to resume. The pane is unchanged.

### A return nobody recorded

Observed 2026-11-17 in headless runs: with a brief that asked for the ticket file updated to done with a log line, 3 of 4 sessions that routed a worker hand-edited the ticket to done and never called `finish`, so the result, what was checked and what is uncertain never reached the log. Weaker models are worse at bookkeeping, so the board does it, and never blocks on it.

- **The return is recorded by the mod.** When an agent whose run carries a ticket ends its turn (the subagent's `turn.complete`), the ticket log gets `returned build run after 4m`, naming the run's category from `sidequest.runs` as the spawn line does (or `returned build run, interrupted`, `, on an error`, `, on a refusal`), and one line per result-contract field read out of the answer: `result`, `checked`, `uncertain`, `needs`, `branch`, `commits`, `changed`. A field opens in any of the shapes models write: `` - `needs`: `` or `needs:`, a bold name, a heading, a table row with the name in its first cell, or a name listing several fields (the scout's `` `branch`, `commits`, `changedFiles` ``). A field it cannot find reads `not recorded`. An answer with none of the fields is kept as the result, cut to 400 characters. No model tokens, nothing per tool call, and a failure leaves the ticket as it was.
- **Returned, not recorded** is a `doing` ticket whose log shows a return of its own category of work after its last start and no finish after that, unless that return was interrupted. The own category is the ticket's, or the one start ran it as when its own had no route. A review run's return in a wave is logged too, but never counts and is never read by the repair, so a reviewer's answer is not taken for the worker's result. It is read from the ticket file alone, so it survives the session. The board tool's summary and the band show it.
- **The board repairs it.** At the end of a main-session turn, once one whole main turn has started and ended after the return (the session's chance to call `finish`), and at session start for anything an earlier session left, the mod makes the move `finish` would make: a failed run (an error or a refusal), or a `needs` that names a need, goes to `needs-you`; otherwise `review` for a build ticket and `done` for any other kind. An interrupted run is left alone: its ticket stays `doing`, its return line says it was interrupted and when, and the pane shows it as started and not running. Moved to `needs-you` it asked the person about nothing. A `needs` that starts with nothing, none or no, says n/a or is a lone dash names none. The log line says `finished <outcome>, recorded by the board because finish was not called`. A `needs` it could not find is read as none, not parked at `needs-you` (that would be the bookkeeping gate the human ruled out), and the line adds `needs not recorded, read as none`. The repair redraws the board and raises the same toast and notification a `finish` would. A ticket whose run has a live agent is skipped: a follow-up message wakes a returned worker under its old id (`agent.spawn` with `resume`), the spawn hook lists it live again, and its next return starts the wait over.
- **What a reload does.** Which tickets are waiting for their turn is kept in the module. A fresh module (a plugin reload, an enable, a worker respawn) starts with that empty, and its `session.start` records every return left on the board at once, a just-returned one included; so does a second session opening on the same project. That is harmless, since a later `finish` appends its lines and moves the ticket again, so it gets no mechanism of its own.
- **A ticket moved by hand is accepted as it is.** Nothing checks how it got to `done`.
- `finish` still adds what the session checked and moves the ticket on its own call, and never repeats a line the return record already wrote.

### Flow

`plan` → tickets on the board → `run` (routed agents, worktree each) → `land` (merge, one verify on the composed tree) → done. Small exact work skips the `plan` skill and the board entirely and says so in one line. Planning is a conversation, and every step ends with something the human can read and correct:

1. **Read first, then find out what is true.** One board read, the whole request with its comments and attachments, the code. A reported problem is reproduced before anything else. A feature gets the code it touches read. An empty project gets research on how such a thing is built.
2. **Show the findings**: everything goes into the story once (short version, analysis, path, excerpts, questions), and the chat says only what the tool's reply hands it: a pointer to the board when the plan view shows, else the short version and the decisions block.
3. **Lay out the options**, each with where it lands in the code, what changes, why and at what cost, plus pushback and what the human may not have thought of.
4. **Check feasibility.** The least certain part is proven cheaply before anyone commits.
5. **Grill**, in rounds, on what only the human can decide. With a person here on work that changes code that includes the design: the interface, where the behaviour lives, what is left out, the seam it is tested at, asked before any plan is shown, a few related questions at a time starting with what the others hang off, with a follow-up when an answer opens a decision.
6. **Agree how it gets delivered**: in checkpoints the human looks at as each lands, all at once, or their own way. It is a decision on the story, and the next story on the board recommends the same.
7. **Record, slice, play back, one yes.** The playback shows each ticket's own text, its technical plan included, and that text is what gets filed, at the playback, as proposed tickets that start on the yes and no sooner. A reply that corrects the plan is not the yes. After that yes nothing asks for a go-ahead.

A checkpoint needs no new mechanism: it is a `hitl` ticket of kind `review` that the next slice is blocked by. A new project starts with a walking skeleton ticket whose check becomes `settings.verify`.

### What a ticket is

A ticket is one outcome the human agreed to. When the problem was big enough to be grilled, the tickets are what the interview produced: each one is a piece the human would recognise from that conversation and can check when it's done.

- **Not too high.** "Rebuild the board" is a story. A ticket is a slice of it that is demoable alone and has a `Done when` check that fails today.
- **Not too low.** How a ticket gets executed is never a ticket. One agent, or a workflow that builds, reviews and fixes: those are runs on the ticket's log. No ticket per agent, per stage, per observation or per measurement gap. Agents never mint tickets.
- **Not always from an interview.** A few known pieces go straight onto the board. A read-only fan-out with nothing to track (a research sweep) can run with route tags and no ticket.

### Who does the work

The main session orchestrates. Anything significant goes on the board, so its status and its outcome are visible to the human:

- Real digging (a reproduction, a measurement, research that takes more than a few minutes) is a ticket of `kind: research`, run by a read-only scout. Its log keeps what was found.
- A quick lookup is a scout with a route tag and no ticket.
- The session does a thing itself when that is cheaper than briefing an agent: a command it already knows, a file it can name.
- **More than one part** (a change with more than one behaviour or touching something another part of the system calls, a reproduction that takes many runs, a batch of items of the same kind) gets one ticket for the whole piece before it starts, also when the session does all of it itself, and the session notes on its log what it found and where it stands. The plan says whether the session builds it or routes its parts; nothing forces routing. One place and a clear outcome stays inline with no ticket.
- **A second reader.** Before a change with more than one part that the session built is called done, one `sidequest:scout` reads it and tries to break it, and the session fixes what it finds or says why not. A batch of independent small items gets none: there it cost more and found less. The reader is spawned with `[route:build]` at the start of its prompt and no ticket ref before it. That is the smallest way onto the mid tier with no setting for the person: `build` is on the standard tier (sonnet, medium) on every board, a `board.json` an older version wrote out in full included, while `review` is on the deep tier and changing its default would reach only boards created from now on. A leading ref on a `build` ticket would make the board take the reader's return for the work's own. Routed tickets keep their `review` run as `run` says.

Observed failures behind this: on 2026-11-17 a session on the older Toolshed reproduced and measured a bug by itself for six minutes on the most expensive model, with nothing on the board, and the human had to ask why. On 2026-11-19, on a top model, a four-commit change and a 49-call reproduction were done inline with no ticket, and the change's status and findings ended up in a notes folder outside the repository. Measured the same day on a small service: one mid-tier reader caught a crash in 2 of 2 runs that 4 of 4 inline runs shipped, for about 75 seconds and 35 cents more per change.

### Workflows go through tickets

A workflow is a way to execute tickets, so it takes tickets in and hands results back.

- Every agent a workflow spawns for a ticket starts its prompt with the ticket ref. A stage may add a route tag: `SQ-12 [route:review]`. The tag decides the route for that stage, the ticket gets the run on its log. With no tag, the ticket's own category decides.
- The `run` skill resolves each stage's model and effort from the routing table and passes them into the workflow, and the prompts carry the refs. So routing holds twice: explicitly in the call, and by the hook if a script forgets.
- A run is recorded on the ticket whenever a ref is present, whoever chose the model: `started scout opus/high (review)`.
- The main session writes the results back with `finish`. Workflow agents never touch the board.

## Quartermaster contracts

### Pipeline

`evidence → candidate → proposal → decision → change → verdict`. Each arrow is code, each noun is a record.

- **Evidence**: events sensed in-process (permission denials, tool failures (a shell failure is named after the command that failed, found by skipping a leading `cd <folder> &&` and taking the last command of a chain, with the words of an error of the setup kept beside it when its output holds one (a command not found, a permission, a missing file or module, a connection, a login); a call the person rejected, which the host marks as any other error and so is told apart only by the words it hands the model, and exit 1 from grep, rg, diff, test and git diff are no failure; a `fix` candidate from a shell failure needs the same command and the same such error to repeat, so a failing test, lint or build is not what makes one, and a failure written before the error words existed is counted but never repeats an error), commands the person typed in bash mode, skill use, long turns, compactions). A typed line is read from the `session.append` row on door `command` that starts with the bash-input tag (read from the 2.1.327 binary, not seen live); a model's or subagent's shell call never counts, and `kind: "command"` events from older builds are ignored. Append-only JSONL, one file per session per day, under `~/.claude/quartermaster/events/<project-slug>/<date>.<session>.jsonl` (older `<date>.jsonl` files are still read). When a write fails twice, that day's events go to `.claude/quartermaster/events/` in the project, which is read too. Never model-visible.
- **Candidate**: a deterministic detector crossed a named threshold ("ran `npm run build:x` by hand 14 times"). No aggregate friction score.
- **Proposal**: `.claude/quartermaster/proposals/P-0007.md`. Frontmatter: `id`, `kind`, `target`, `status`, `authority`, `evidence`, `expect` (a countable check and its baseline), `created`. Body: what, why, the exact diff or command, the rollback.
- **Decision**: approve, reject (with reason, kept in `.claude/quartermaster/rejected.md` and never proposed again), already handled (status `handled`, closed with the person's reason and the day it was answered, written to no never-again record; its evidence settles candidates, on the list and for the resupply round offer, only while the 30-day evidence window counted from the day it was answered still covers it, a file with no answered day counting from the day it was made, so the same thing piling up after that may be proposed again), or later. Silence is recorded as silence.
- **Change**: `.claude/quartermaster/changes/C-0007/` holds the record and the prior bytes of every file it touched. Rollback is a file restore.
- **Verdict**: a status ladder, `applied → loaded → exercised → useful`, then `keep`, `improve` or `roll back`. A change nobody ever exercised is a failed trial, and retiring it is a normal outcome.

`kind` is an enum: `skill`, `skill-improvement`, `rule`, `permission`, `setting`, `plugin`, `routing`, `script`, `retire`, `upstream`, `docs`.

The scan tells the installs apart by version, never by marketplace, because both versions come from one marketplace, `eigenwise-toolshed` (`scripts/toolshed-installs.mjs`): under that name a plugin below its first major of this line (sidequest 7, quartermaster 2, codebase-mapper 3, live-rules 3, observability 2) is the older version, `quality-gate` and `model-gateway` are older at any version, and a plugin at or above it is this one; `toolshed-next`, the name this version had before it took over, is the third state, `earlier-name`. The older version is not installed beside this one: it arrives by a normal plugin update under the same ids, which changes nothing in a project, so the product says so once. Each plugin tells its own leftover once per project, Quartermaster for all when it is installed, and a plugin running from `toolshed-next` also gets the commands that move it, once per machine (`shared/older-toolshed.ts`, synced into each plugin). The run never acts against its own marketplace: it never disables, uninstalls or removes a plugin of a shared name under `eigenwise-toolshed`, never removes the marketplace and never takes it out of a project. The earlier name moves once for the machine, in a fixed order (uninstall under `toolshed-next`, remove that marketplace, add or update `eigenwise-toolshed`, install again at the same scope), then the project files that name it are rewritten. The gateway is unwired everywhere before it is uninstalled, because its wiring runs a launcher found through its install, and an uninstall with a place still wired blocks every prompt there. `model-gateway` is not in this marketplace, so it must stay installed and switched on until the upgrade has unwired it. `UPGRADING.md` at the root is the door.

Quartermaster proposes, configures and improves. It owns no runtime gate, no scoring and no orchestration.

### In a project that already has a team and tools

Most projects are not empty, and one person must be able to try this without changing anything for teammates.

- **Personal first.** In a team project (other git authors, a committed `.claude/settings.json`) outfit installs at local scope until the human says the team adopts it. A project-scope install is a team decision and declares the marketplace with it.
- **Never two of the same name.** A plugin with our name enabled from another marketplace (a fork, a copy) is a clash: both would load, their skills share a namespace, and the other one's hooks fire on our work. Outfit offers to disable the other one at the scope it is enabled at, and overrides a team-enabled one at local scope instead of editing the team's file. `inspect` reports a clash and which of the two a session is really running. The older Toolshed is not a clash: it shares our marketplace name and is told apart by its version (`scripts/toolshed-installs.mjs`), so outfit says to update it and the upgrade handles what it left.
- **The team's own things stay.** A committed map or rules from another tool, and the project's own skills and rules for issues, branches, pull requests and release notes, are left in place. Sidequest's `land` delivers through them and keeps their approval steps.
- **Personal records stay out of git.** `.sidequest/` excludes itself through `.git/info/exclude`. So does `.claude/worktrees/`, at a start that returns a worktree call, when neither that file nor the root `.gitignore` lists it, read as text with no git process and said once (observed 2026-11-22: after the first worker, `git status` in the main checkout listed the folder, so a `git add -A` would stage a nested checkout). `.claude/quartermaster/` ignores itself with its own `.gitignore`, because it holds the saved bytes of touched files, local settings among them.
- **Worktrees are a default, not a requirement.** Where a worktree lacks ignored files or running services, `settings.worktrees: false` runs workers one at a time in the main checkout (each holds `checkout`, so scouts still run beside them), each on its own branch unless the brief's delivery rule says to commit on the checked-out branch. A worktree starts from the remote branch unless `worktree.baseRef: "head"` is set, so setup and the run skill offer it, in `.claude/settings.local.json` by default, where local commits are unpushed. It offers `worktree.symlinkDirectories` only where a directory symlink works, and says so where it does not (Windows without Developer Mode). Both are offered, approved and reversible.

## Observability contracts

**The boundary.** Measuring is this plugin's job and no other's. Quartermaster never records; it may read the ledger later, as a reader. Nothing else in the tree needs this plugin, and it needs none: it reads Sidequest's `sidequest.runs` when that is published and writes a row with no `spawns` field when it is not.

**Why it is here.** It was dropped on 2026-11-22 for want of a named need. A team then switched the older version on, and the owner decided it comes along: per developer, local, under the same name, as 2.0.0, so an install of the older one updates in place at the switch and keeps its history and its switch. `.out-of-scope/observability.md` has both dates.

- **Off until switched on.** `/track on|off|status` sets and reads the switch in the plugin's own store under `track:<project root>`, the older version's key, so a project that recorded keeps recording after the update. Nothing is recorded before `on`, and `status` names the ledger file. The project root is the repository root, else the session's folder, so a worktree records with its main checkout.
- **One file per session.** A finished main turn appends one row (`v: 1`) to `<config dir>/observability/ledger/<project>-<hash>.<session>.jsonl`: the host has no append call, so a turn reads and rewrites its own session's file, and two sessions in one project never rewrite each other's (the older version kept one file per project, which two sessions rewrote whole). A file past 3 MiB is rolled aside as `<name>.<millis>.jsonl`, under `$.fs.read`'s 4 MiB limit. The config dir is the shared rule (`CLAUDE_CONFIG_DIR`, else `.claude` under `USERPROFILE`, then `HOME`).
- **Every older row is read.** The usage page and the report read both name forms (the older `<project>-<hash>.jsonl` with its rolled-aside files, and the per-session ones) in both config folders: the shared rule's, and the older version's, which looked at `HOME` before `USERPROFILE`, where the two differ. A `quality` field on an older row is never read.
- **The session's name is the person's words.** The first line of the first prompt the person typed (`composer`), sent from the phone (`bridge`) or gave a headless run (`sdk`) names the session, and a leading ticket id sets the turn's ticket. Another session's message, a task notification, a schedule, a plugin's prompt, a slash command and a prompt the person never saw never do: the older version took any of them, so a session could be named after another session's message.
- **Its commands are bare names, and none is `board`.** A command a plugin registers is one bare name for the whole session, typed as `/track` and `/usage-page`: no `observability:` goes in front, and a second plugin that registers a taken name is refused (seen on host 2.1.332: `"/say" refused: the plugin probe registered it already`). The older version named its page command `board`, which is the work board's command here, so with both plugins installed the host refused whichever registered second and that plugin's start stopped at the refusal. So the page's command is `usage-page`, each command is registered by itself, and a name another plugin holds costs that one command and a status line saying so. Sidequest's start draws the board all the same when `/board` is taken, says once that it opens from the band, and keeps the band's button there on a quiet board too, where the band otherwise stays away.
- **The usage page is built on demand.** `/usage-page` reads the last 90 days of every ledger, writes `<config dir>/observability/board.html` (the older version's file name, kept so a bookmark still opens it) in one write and opens it only when typed at the terminal (`composer`); from any other origin it answers `observability: usage page written to <file> on this computer; open it there.` Nothing else writes the page: the older version rebuilt it on a two-second timer after every turn, which a headless run could end mid-write. The page is self-contained, with no network call, and its script is the folds and page functions inlined by their own source text.
- **Every hook fails open.** One in-process module, no command hook, nothing per tool call but an in-memory tally. A failed ledger write pins one status line, which the next good write clears.

## Cross-plugin contracts

- **Provider file**: `<config dir>/toolshed/providers/<name>.json` (the config dir is `CLAUDE_CONFIG_DIR`, else `.claude` under the home folder) with `{ "name", "models": [{ "id", "label" }], "fallback" }`. A provider plugin writes it. Sidequest only reads it. The words for any specific provider never appear in Sidequest.
- **Outside code and a worktree.** In real sessions on 2026-11-19 the reviewer was used in 3 of 5 and a passed branch ran in a container in 0 of 5: every session that got a pass tested it in a throwaway worktree on the host. So the front door says in one sentence that outside code runs nowhere on the machine before the reviewer passes it and only in the container after, and that a worktree is not isolation, and the reviewer ends a pass with the same.
- **Models from other providers are not built yet. This version ships with Claude models only, and other providers are the first story after the release.** No plugin writes a provider file today, and setup and outfit say nothing about providers (`.out-of-scope/non-claude-models.md` has the evidence, where the old plugin is in history and what must stay open). So nothing may assume every routed agent is an in-process subagent on a Claude model, and whether Remote Control can work in a setup is part of that feature. The way in stays open. A provider file makes its model ids legal tier values. A tier on such a model would run as its own process on the provider's endpoint: there is no way to do it in process, but a separate `claude -p` with its own base URL works against a stub. Until that exists, such a tier falls back with a named reason.
- **State keys**: `sidequest.summary` (`{ needsYou, ready, doing, review }`) and `sidequest.runs` (agent id to `{ ticket?, category, model, effort, requestedModel, toolUseId? }`: `model` is what the agent runs on, `requestedModel` is what the route asked for, `ticket` is absent for tag-only spawns, `toolUseId` is the `Agent` call that spawned it and is absent for a workflow's agents). Readers treat a missing key as "not installed".
- **Result contract**: what every routed agent returns. See `shared/result-contract.md`.
- **Grilling**: one primitive, `shared/grilling.md`, copied into the skills that use it by `scripts/sync-shared.mjs`.
