# Contributing to Eigenwise Toolshed

## Base branch

Pull requests target `develop`, not `main`. `main` is written only by the release cut: a
reviewed promotion PR moves a prepared release from `develop` to `main`, and nothing else
pushes there. Open your PR against `develop`.

## Release fragment

Every behavior change ships a release fragment at `.release/unreleased/<REF>.md`, in the
format documented in [`.release/README.md`](.release/README.md). Generate it with:

```bash
node scripts/release/note.mjs <REF> --title "..." --plugins <plugin> --bump patch|minor|major --commit "$(git rev-parse HEAD)"
```

Repository-only work (release scripts, CI, docs) uses `--scope repo` instead of `--plugins`
and `--bump`. If you do not have a board ref, say so in the PR description; a maintainer will
assign one and add the fragment.

Never hand-edit a plugin or marketplace version. `scripts/release/cut.mjs` owns every version
bump; a fragment is the only input a PR provides.

## Agent-facing surfaces move with the behavior

Most of what this repo ships is read by agents, not people: MCP tool schemas and
descriptions, refusal and guidance strings, agent and skill definitions, CLI help, and live
rules. If your change alters any of these, update the string in the same PR as the behavior
change, not as a follow-up. See `CLAUDE.md` for the full rule. When a value is enumerated in
code, that enum is the source of truth for every surface that repeats it.

## Generated docs

Pages under `docs/src/content/docs/reference/` are generated by
`docs/scripts/generate-reference.mjs` from plugin manifests, skill frontmatter, hooks.json,
and the marketplace file. Never hand-edit them. If a generated page is wrong, fix the
generator or the source manifest and run `npm run generate` from `docs/`.

Human-maintained prose (getting started, setup guides, observability, architecture,
[contributing](docs/src/content/docs/contributing.md),
[release process](docs/src/content/docs/release-process.md)) lives under
`docs/src/content/docs/` and is updated by hand in the same PR when the workflow it
describes changes, or through a linked `docs-writing` ticket filed before the change ships.

## Verify your change

Each plugin has its own suite:

```bash
cd plugins/<plugin>
npm ci
npm test
```

Sidequest is the exception: it has no `test` script, run `npm run test:full` instead.

## Quality gate

Every function a change adds or modifies is expected to score a CRAP below 6, where
`CRAP = complexity^2 * (1 - coverage)^3 + complexity`, measured per function from real
coverage, not estimated. Untouched legacy functions are out of scope; a review does not
ask you to fix debt you did not touch.

The committed runner, `scripts/quality/crap.mjs` (`npm run quality:crap` from
`plugins/sidequest`), is being aligned to that standard and does not enforce it exactly yet:
today it flags a new function only at CRAP 8 or above, and an existing function only when its
CRAP rises above its baseline on `develop`, rather than requiring every touched function to
clear a strict below-6 bar. Use it to measure your change, but the number the runner prints
and the number a review holds you to can differ until that alignment lands.

## Negative controls

When a fix changes behavior, show the reviewer the bug you fixed, not just the passing test:
describe or demonstrate what fails without your change (a reverted assertion, a command that
errors, a repro that no longer reproduces), not just that the suite is green afterward.
