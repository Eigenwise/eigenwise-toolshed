# Patterns

Last Updated: 2026-10-08

- Build from source, run committed output: Sidequest TypeScript under `src/` compiles to `lib/`, `bin/`, and bundled hook files, while `scripts/generate-bundled-agents.mjs` renders the committed `agents/` roster from `lib/agentsync.js`. Runtime manifests point at generated files; release suite discovery is shared through `plugins/sidequest/lib/suite-resolver.js` and re-exported by `scripts/release/lib/suites.mjs`.
- Stable executor packaging and migration: the Sidequest plugin owns its generated diagnostic, dispatch, and read-only agent definitions in `agents/`; session-start maintenance and normal CLI sync remove only marked legacy generated files from user agent directories, preserving custom content.
- Bounded context projections: Sidequest freezes dispatch contracts and pages large MCP reads with opaque revision-bound handles; callers continue through `context_page` and rerun mutable reads when a revision is stale.
- One store, multiple transports: Sidequest CLI and MCP handlers call the same store functions. Keep lifecycle behavior in typed kernel reducers and store transitions rather than duplicating it in transports.
- Immutable candidate lifecycle: preparation pins baseline and executor identity; submit atomically records the candidate, terminates the executor, and releases its claim. A confirmed review defect preserves and permanently rejects that candidate. A repair has a fresh identity and supersedes the rejection only after integration. Bound-review outcome guidance names the candidate as the subject: accepted approves it, rejected prevents shipment, and prose cannot override the enum. Finalized acceptance can be corrected through main-only `verdict.correct`, which requires the exact original verdict time, source, candidate and rejection evidence (`src/lib/mcp-review-correction.ts` and `src/lib/store/review-corrections.ts`). Dispatch token replacement is staged inside the locked transaction and the prior token is retired only after COMMIT; a rollback removes just the staged file. A repair explicitly linked `related` to a source whose exact candidate carries an oracle-confirmed rejection is the one exception: it can submit the full range that inherits the rejected candidate's commits (`inheritedRejectedAdmission` in `mcp-lifecycle.ts`), keeping the inherited commits so delivery and per-path supersession still see every byte. An `apply`-mode delivery leaves its materialized tree uncommitted; committing it and binding it with `groomClose ... deliveryCommit` completes the same delivery record, and a verifier failure during that binding leaves the delivered record retryable rather than marking it failed (`applyDeliveryAwaitingContentCommit` in `store/submissions.ts`). A delivery commit that is not itself reachable because the candidate was rebased or squash-merged before landing proves content at a named `deliveryRevision` instead, with `resolvedPaths` required for every hand-resolved path and refused once the delivery commit already answers for itself by reachability (`deliveryRevisionPreflight`, PR #146); short of that, a reachable merge falls back to `git patch-id` equivalence over the whole submitted range for a squash merge whose one resulting commit has no per-commit patch to match (SQ-3113).
- Composition adoption is a one-use, locked control-plane grant, not proof of historical checkout ownership: `update.admitComposition` requires the main-session grant; its audit `by`/`evidence` labels confer no authority, and an omitted `expected` returns a write-free snapshot for compare-and-set retry. Admission requires a genuinely released root and pending terminal submissions from distinct `related` sources, with current authoritative review/correction identities. `proveCompositionRange` in `store/composition-range.ts` requires the full original `BASE..C` to equal every pinned source range plus the root's own commits and exact in-scope paths; the original release fragment must already exist in C. Dispatch rechecks under locks and consumes the grant for one nonce and fresh isolated checkout at C, while capture and submit bind exact C and the new checkout; source state is rechecked at active and delivery boundaries, and delivery requires independent review of the exact submitted C. Historical checkout ownership stays unverified.
- Bound review records remain protected from deletion: `store/tickets.ts` checks direct, reverse and partial bindings on a fresh locked read, with source-first lock ordering. Completion, archive/restore and force do not permit deleting a bound source or review. Unbound deletion removes attachment files only after the database transaction commits, so rollback preserves the row and bytes. This prevents new orphaned bindings; it does not repair existing ones.
- Fresh dispatch reconciliation: primary SessionStart retires only launched dispatches for the current session that have no bound runtime identity or claim, then reports those refs for redispatch; bound or claimed attempts remain protected.
- One retirement authority for every unclaimed-attempt route: `dispatch --recovery-evidence`, `--retire-only`, `groomClose` with `recoveryEvidence`, `pulse`, and `groom-close` all read the same claim-grace deadline (`claimGraceMs`, `SIDEQUEST_CLAIM_GRACE_MIN`, default 15 minutes, clamped to the idle backstop) measured from an attempt's latest runtime signal: launch, WorktreeCreate start/completion, finished provisioning, bind, briefing fetch, claim, or a trusted same-session board write under the bound runtime name after launch and before any claim. An attempt whose WorktreeCreate never recorded finished provisioning never becomes grace-retirable, because a cold `npm ci` looks identical to a dead hook; it only reaches the longer idle backstop. WorktreeCreate's five per-checkout callbacks (completed creation, finished provisioning, provisioning failure, dependency link, and recovery) are generation-scoped and refuse as `stale_attempt` or `missing_attempt` instead of stamping a replacement attempt that reused the same session and checkout; the start binding itself cannot be generation-scoped because the hook learns its generation from that call, so it stays scoped to the session and checkout instead.
- Adapter-owned facts: Git repositories and non-Git projects resolve immutable candidate existence and baseline membership through registered capabilities. Callers cannot assert those facts, and an unavailable adapter fails closed while preserving the retry candidate.
- Lease every checkout: worktree operations require repository, dispatch baseline, bound path, checkout-instance digest, phase, and liveness facts. Paths, branches, sessions, and process presence are hints rather than cleanup authority. Resuming a retained checkout additionally refuses one with unmerged index entries or an in-progress cherry-pick, merge, revert, rebase, or bisect: a conflict does not move HEAD, so a stuck replay still matches its release-time identity and would otherwise hand the replacement executor a partial candidate (`retainedWorktreeResumeDecision` in `worktrees.ts`). Nothing is auto-resolved; the conflicted checkout is preserved as failed-replay evidence and the replacement executor gets a fresh isolated checkout instead.
- Provider routes come from one capability decision: Sidequest accepts only fresh, valid, ready schema-4 Model Gateway catalogs for routing and model advertisement. Provider metadata may survive for precise refusal messages; stale or unready entries never materialize GPT defaults. Explicit provider-crossing overrides use the existing `dispatchReadOnly` authority, including ticket-level overrides, and are allowed only for effectively readonly work. Writable crossing and automatic cross-provider fallbacks remain refused; later edits cannot change an already-prepared readonly executor, route or review binding. Every dispatch prompt ends with a `[sidequest-route model=... effort=... ticket=SQ-n]` marker; Model Gateway reads the ticket field into its usage rows, so gateway spend is attributable per ticket without parsing transcripts.
- Isolated worktree creation resolves the board from the spawning checkout, falling back to the session's own reserved dispatch repository when that checkout cannot bind, so a cross-project isolated dispatch is still cut from the ticket's own repository; prepare-time refusal now fires only for the genuinely ambiguous case, a session holding launched isolated dispatches on two boards at once, and names both paths and the `sharedTree:true` escape. Tests that dispatch temporary boards run the call from the board's checkout.
- Lifecycle MCP calls that omit `project` resolve the board the same way, from the caller's own binding, when more than one board is registered: the dispatch's own worktree for an isolated dispatch, or the claim owner named by `by` for a shared-tree one (`resolveLifecycleProject`/`boardBindsCaller` in `mcp-shared.ts`). A caller bound to more than one board refuses and names them; a caller bound to none stays on the spawning session's board with its existing refusals unchanged. A call that takes no `worktree` argument (comment, release, done, claim, plan, scope requests) needs `project` to reach a sibling board.
- Integration targets belong to the ticket's recorded dispatch: submit, wave assembly and delivery resolve that target through `ticketIntegrationTarget`, falling back to board configuration only when no target was recorded; `deliveryIntegrationTarget` in `store.ts` then lets a delivery follow the checked-out branch when it is, or descends from, the recorded one, or an explicit `integrationBranch`, and the integration record's `targetBranch` names the branch actually delivered to. `commit-scope.ts` derives qualified local and frozen remote proof refs; range validation carries target mode through submit and queue reads so same-named tags cannot shadow the upstream. Equivalent-patch and content checks use the same matched ref and commit. Missing required remote proof fails closed; an absent optional local branch cannot mask remotely landed work during abandonment. Mixed-target waves refuse; source-revision invalidation returns a structured refusal without assuming a Git branch. Candidate overlap is judged on the candidates' real changed paths, not on intersecting declared scope directories, and a refused integrate names the manual pinned-candidate route (local merge, gate, then `integrate` with `deliveryCommit`). Synthetic delivery tests configure their actual board target and restore prior configuration instead of fabricating caller-supplied target objects.
- Per-request pricing stays close to usage: Observability selects Astra's short or long input tier from each request's input/cache totals, while unpriced resolved models are grouped as token volume and excluded from USD totals.
- Verify produced behavior: ticket oracles observe the required property on output. Implementation-name greps are diagnostics, and overlapping terminal waves rerun the property oracle after assembly. Commandless shared-tree or external-deliverable requirements close with typed `done.verify` evidence, forwarded through `externalDeliverableCloseout`; command and suite requirements stay bound to their matching verify-capture, and review verification is refused for working-tree delivery. verify-capture refuses to even run the pinned command over a dirty worktree, not only to record the capture afterward, except for a working-tree-delivery target identified by the content hash of its own uncommitted paths. Single-ticket wave admission reuses the candidate's submit verify-capture instead of re-running the pinned command, but only when that capture recorded a clean worktree at the candidate's committed content; a capture taken over uncommitted edits, and any capture recorded before that field existed, falls back to provisioning a worktree and running the command. Delivery still runs its pinned verifier. Executor and publishing guidance use focused editing checks, one final clean-candidate capture, and one combined full gate after wave integration before versioning; a changed rebased tree needs a fresh gate. Required contract-named or safety-sensitive reviews remain pre-delivery. Compatible candidate coverage can be reused by the local quality owner without a coverage-only rerun.
- Environment lane for verification: a board declares `verifyEnvironment: isolated | shared` (`src/lib/store/config.ts`, served in `board_config` by `src/lib/mcp.ts`), and dispatch pins the resolved environment into the ticket's verification requirement (`src/lib/store/dispatch.ts`: `liveVerificationRequirement`, `applyLiveVerificationRequirement`, `recordVerificationAmendment`). Under `shared`, executors do not run the pinned command or suite; the delivery gate at integrate runs it in the shared checkout against the merged tree, and the verification status `deferred` (`src/lib/kernel/verification.ts`) is visible and never counts as accepted (SQ-3423, SQ-3457). W3 (SQ-3490, story US-79): MCP `integrate` refuses an environment-bound verifier with `environment_lane_requires_cli`; the CLI delivery gate runs the shell under `scripts/owned-process-tree.js`, whose Windows job owner (`scripts/windows-job-owner.cs`, compiled on demand) receives its report path and a per-run nonce through argv only, scrubs them from the verifier's environment, and stamps the nonce on every record including the final `done`; `readJobReport` accepts only nonce-matching lines, so a missing `done` or a nonce mismatch yields survivor state unknown, never none. Verdict order in `src/lib/ports/process.ts`: timeout (exit 124), missing done as `could_not_run`, verifier failure as `failed_suite` with its exit code plus any cleanup text, cleanup error alone as `could_not_run`, then passed. The nonce defeats accidental forging only; a same-user verifier can always read it (SQ-3492 ruling), so deliberate forging is left to candidate review. W4 (SQ-3426, a one-time bounce of a failed lane run back to todo with the log) and W5 (SQ-3427, executor and skill text) follow.
- No child process inside a board write transaction: `withinTransaction` (`src/lib/store.ts`) is the single funnel for store writes and `withTicketLocks` wraps every ticket-locked body in one `BEGIN IMMEDIATE`, so a git call or lock-file wait inside it holds every board's writers past their busy budget (the 2026-10-08 lock storm: six executors, every orchestrator write refused after 6.2 s). SQ-3499 moved `claimTicket`, `completeDispatchWorktreeCreation` and `recoverDispatchWorktreeCreation` to the shape the guard prescribes (read git facts before the transaction, pass them in, re-check the rows inside against the existing refusals; later writes through `afterCommit`), deleted the redundant `.meta.lock`, and made the all-writes guard (`guardedWrite` in `src/lib/db.ts`) enforce under the test harness via `SIDEQUEST_GUARD_ALL_WRITES=1` (set by `test/_sidequest-test-home.ts`) while production keeps the opt-in; the openers that still spawn are listed by name in `db.WRITES_STILL_SPAWNING`, each tagged with its follow-up (SQ-3524 verify-complete checks, SQ-3525 composition and integrate, SQ-3526 submit and capture, SQ-3527 dispatch binding and stops), and SQ-3528 flips the default and deletes the allowlist. `test/write-lock-git.test.ts` is the regression suite.
- Shared verification-slot classification: `src/lib/verify-capture.ts` recognizes `npm`, `npm.cmd`, and `npm.exe`, prefix/workspace selectors and quoted selector paths before `run test:full` or `run quality:crap`. Scoped and unrelated commands stay outside that full-suite slot. Classification schedules work only; it supplies no quality, capture or review authority.
- Resource and comment handoff guidance requires observed evidence: shared-slot return requires actual owned-command completion and descendant cleanup. A comment cursor records processed instructions rather than merely received timestamps.
- A suite answers for its own checkout: ambient environment is what makes a local run disagree with CI, so `plugins/sidequest/test/_sidequest-test-home.ts` pins `SIDEQUEST_HOME`, the git config vars, and (through `test/_hook-runtime.ts`) `CLAUDE_PLUGIN_ROOT`, which hooks resolve `lib/*.js` under. Without that pin a suite spawned from a plugin-hosted process runs its hooks against the installed plugin while its assertions drive the checkout. `suiteEnvironment()` in `scripts/release/cut.mjs` strips the same variable along with the session and agent identities and every credential before any release or verification suite runs. A test needing a different identity or root sets its own.
- Serialize board mutations: MCP mutation handlers enqueue per-board work before touching state.
- Preserve exact ownership: Sidequest reclaims claims and pre-claim dispatch bindings only after confirmed terminal process evidence, keeps unknown owners protected, and checks ownership before forced submission, release, or rejection-history mutation. `src/hooks/subagent-stop.ts` reports a held claim as `exec WAITING`; if name addressing fails, only the recorded original session may send once to the exact recorded native agent ID. Missing addressing remains `UNVERIFIED`, with claim and work preserved. User Pause retries stops sends. Model Gateway applies the same floor to startup, recovery, restart, and drain; bounded unknown or foreign port owners remain untouched, and POSIX `ps -ww` preserves the command text needed for install-root checks. POSIX probes run their child with `LC_ALL=C` so `lstart` parses under any user locale; Windows inherits its environment.
- Cleanup preserves recovery authority across sweeps: `plugins/sidequest/src/lib/worktrees.ts` renames reclaimable trees into quarantine before destination checks. Observed unpinned detached commits remain retained; containing refs exclude branches the same sweep may delete and private ref namespaces. Each invocation reconciles retained parked registrations with native Git repair before metadata pruning; unresolved registration or unavailable recovery inventory defers pruning, and a later safe empty sweep completes it. Expiry deletes files without following junction targets, then permits metadata-only pruning when safe. Named branch deletion uses atomic compare-and-delete against the observed tip; same-value ABA and new writes after final checks remain outside that guarantee. Retention is age-based with live-owner protection, without the retired per-agent count cap.
- Owned process phases: `plugins/sidequest/scripts/owned-process-tree.js` starts each gate under a detached supervisor, classifies terminal process and group states, bounds retained output, and delays settlement until cleanup evidence is drained. Unknown or still-live ownership remains blocking. On Windows the direct-leaf path (`runDirectlyOwnedPhase`, `signalOwnedLeaf`) takes a caller `AbortSignal`, rejects pre-aborted input before spawn, terminates through the retained `ChildProcess` on cancel or deadline, and settles only on the real exit event; a live child `'error'` is an explicit cleanup failure, never success (SQ-3396). That covers the one retained child only; arbitrary-descendant containment for `verify-capture` is separate work.
- Batch-local Stop responsibility: each plugin deduplicates only its own Stop work using stable inputs; mutable transcript metadata and prompt identifiers do not define responsibility, and stale lock cleanup is generation-bound.
- Freshness checks are advisory and version-keyed: Quartermaster refreshes marketplace data at Stop and reports updates or reloads without installing, blocking, or repeating the same version warning. Its mutating updater and migration preflight the Claude executable once before any update mutation; an unavailable executable stops with the existing `--claude` override guidance, while check and dry-run remain nonmutating.
- Atomic gateway updates and request recovery: Model Gateway stages proxy replacements, renames atomically with rollback, compares serving versions, and defers restart when the listener cannot exit immediately. An active request can start or recover the shared proxy without waiting for another Claude SessionStart.
- A refusal names a command the reader can actually run: Model Gateway's readiness and auth messages live once in `plugins/model-gateway/lib/runtime.js`, keyed to the stable `~/.claude/model-gateway/model-gateway.js` launcher, and `commands.js` plus `request-worker.js` import that table instead of composing their own. Codex authentication failures are rewritten on the forward path so the client sees that command instead of the upstream proxy binary that is never on PATH, with the real HTTP status and the upstream detail preserved alongside the instruction. Anthropic passthrough responses are never rewritten, and a 403 is treated as an auth failure only when its body says so.
- Shared-tree artifacts are marker-gated and confined to an approved artifact root. Closeout can exempt disjoint sibling allocations only with matching recorded session, shared checkout and valid overlapping intervals. Completed sibling candidate/content integrity is validated before dirty inventory; missing, restored or committed-away paths cannot evade it. A mismatch refuses with `working_tree_sibling_integrity_violation`. Unallocated drift stays blocked with preserve-and-hand-back guidance, never instructions to revert someone else's work or broaden scope.
- Hook registration is declarative: events and matchers live in `hooks/hooks.json`; source or generated hook code implements behavior. Codebase-mapper blocks an announced map update until the matching Skill invocation is recorded.
- Generated docs are disposable: `docs/scripts/generate-reference.mjs` owns `docs/src/content/docs/reference/`; edit manifests or the generator instead.
- Stream oversized inputs, never load them: quartermaster's miner reads transcripts line by line into bounded collector state and emits aggregates, because one session runs to tens of megabytes. Quotes, titles, and paths are clipped in one place as they are collected, so no reporting path can leak a whole transcript into context.
- Poll local APIs: the dashboard uses HTTP JSON endpoints and a 2.5-second polling layer, with no browser-side SQLite or WebSocket dependency. CI watch failure alerts exclude skipped and neutral conclusions without treating either as successful verification.
- Keep project opt-in local: Quartermaster writes project-local settings, and Observability writes telemetry opt-in state, rather than machine-wide configuration.
- One export authority, and denial outlives the process: repository consent is enforced at Observability's store ingest, and the observer outbox is the only path logs leave the machine by. The Collector keeps trace and metric sink pipelines but has no `logs/sink` pipeline, because a static YAML pipeline cannot follow a mutable consent file. A denial is persisted as a `consent_denial(session_id, denied_at)` tombstone in `plugins/observability/lib/observability/consent.js` and consulted when the session map warms, so an observer restart cannot resurrect a denied mapping; re-opting in clears it. Denied spool rows are retained rather than deleted. Gateway usage rows whose `project_id` is not a hex64 id are treated as a project NAME resolved against the session map and fail closed on mismatch, so a name cannot borrow another session's consent.
- One project identity, hex everywhere it is an id: ingest requires `SAFE_PROJECT_ID` (hex 32-128 or `hmac:`) and rejects the whole observation otherwise, so every emitter sends the repository SHA-256 as the id and the sanitized basename as a separate `project.name` label. `plugins/observability/bin/project-telemetry.js` writes both into `OTEL_RESOURCE_ATTRIBUTES`, matching what the hooks already derive. Because a repository keeps emitting its old value until somebody re-runs the enable command, the Grafana generator (`plugins/observability/observability/sinks/grafana/dashboard-generator.js`) matches `project_id` against the union of each project's id AND name; that name half is transitional and can go once every wired repository has been re-enabled. Loki keeps matching `workbench_attribute_project_name` on the name, which is a different label and not part of this.
- A review needs two proven runtimes, and the two bind sources are not symmetric: `plugins/sidequest/src/lib/kernel/review-binding.ts` compares immutable terminal attempt snapshots and admits a pair only when the candidate and its bound review came from provably different runtime identities. A hook-bound attempt carries a real `agentId`; a `claim_token` attempt never does, only `agentName` plus `tokenPrefix`. Accepting a claim-token attempt as an identity on BOTH sides would let two same-session siblings review each other, so it stands as an identity on one side only. Attempts predating the `bindSource` field fall back to `boundAt`, because refusing them outright deadlocks candidates that were already submitted and reviewed.
- Cap an unbounded scan, do not narrow what it hashes: `plugins/sidequest/src/lib/source-revision-capability.ts` bounds the non-git filesystem snapshot with a path cap, a byte cap and a wall-clock deadline (500 / 64 MiB / 10s), refusing through `FilesystemSnapshotLimitError` and naming the bound, the observed value and the recourse. Narrowing what the walk hashes was first refused because the digest is a persisted baseline identity; GH-334 then did narrow it, skipping `SNAPSHOT_SKIPPED_NAMES` (`.git`, `node_modules`, build output, `vendor`) and root `.gitignore` rules, because counting them put a 19-file repository over the cap, and the larger fix is that a board whose folder became a git repository migrates to the `git` adapter (`adoptDerivedSourceRevisionAdapter` in `store/projects.ts`) instead of snapshotting. A cap refusal now names bounded samples of what was skipped and counted. The deadline is enforced from outside the process because it has to be: a blocking `readFileSync` (a cloud-sync placeholder hydration) is uninterruptible in-process, and `worker.terminate()` does not stop a worker sitting in a synchronous syscall. So the walk lives in `source-revision-snapshot-child.ts`, run through `spawnSync` with a timeout, and the child names each path on stderr before reading it so the deadline refusal can report the file it died on.
- A protected release is prepared from `develop` by `scripts/release/cut.mjs`, promoted into `main` through a reviewed PR, then finalized by `scripts/release/finalize.mjs` at the exact remote `main` head. Finalize derives moved versions from the merged commit's first parent, tags that explicit sha, and prints the sync-back PR; `scripts/release/guard.mjs` grants sync-back exemptions per release-owned path only when the resulting tree entry has the same blob and mode as the pinned publish commit. The Sidequest publish lock serializes participating publishers but cannot close the unrelated-writer tag-only remote race.
- Compaction diagnostics are metadata-only: `plugins/model-gateway/lib/request-worker.js` identifies Claude compaction requests, buffers and retries a Codex SSE stream before visible output within a byte cap, then records bounded outcome, terminal/error/status, and usage fields in `codex_gateway.route`; summary text, prompts, and raw responses stay out of telemetry. A Codex context overflow (HTTP 413 / `request_too_large`) is normalized with the measured request size, the route's limit and the phase (first request, continuation, compaction) in both the response and the telemetry row, and a first request that is already too large says the recovery is upstream (a smaller briefing or a larger-window route) because there is nothing to compact (SQ-3446). The per-request route and chunk bookkeeping lives in a `WeakMap` keyed by the request, so the long request handler itself stays byte-identical. `request-worker.js` holds the only route-marker parser; the duplicate in `commands.js` was removed (SQ-3419).
- Provider context settings distinguish a window from a direct maximum: `runtime.js` reads optional Codex/Grok `compactAt` settings, and `context-window.js` updates `{backend, field: 'window' | 'compactAt', value}` without dropping the other field. Explicit maxima supersede the reported legacy trigger environment value, avoid the legacy85000 subtraction and retain saved-cap/provider-derived bounds. Removal restores legacy policy. The sentry uses previous-response usage, so crossing turns and compaction can exceed272k/2x; the shared warning makes no per-request guarantee. Claude uses its supported separate native window, with exact native cutoff and same-model role separation unverified. Invalid, null and unsupported explicit fields refuse without writing settings.
- A transient commit is proved by its tags, never by its own shape: `unpublishedReleaseTip` in `plugins/sidequest/src/lib/commit-scope.ts` refuses a dispatch baseline sitting on a release commit that is about to be rewound, and it decides that from ANNOTATED tags pointing at the commit (`%(objecttype)` = `tag`, so a lightweight tag never counts) whose set matches a marketplace `v<semver>` plus at least one `<plugin>-v<semver>` BY SHAPE, never by a hard-coded count, combined with non-reachability from `refs/remotes/origin/<integration branch>`. The commit message, author, parent count, reflog and an emptied `.release/unreleased/` were all evaluated and rejected as distinguishers because each is user-controlled or absent. The cut itself tears the window down (`scripts/release/cut.mjs`), so this refusal is normally only visible mid-cut; it earns its keep when that rollback fails. Residual known cost: the reachability half reads a local remote-tracking ref, so a checkout that has not fetched a push made elsewhere can refuse a baseline that is in fact published. It fails safe and names its reason.
- Quartermaster setup seeds an adapted reuse-first implementation baseline and self-improvement live rule; setup and resupply share `skills/setup/references/host-capabilities.md` to distinguish the target host's native support, installed configuration, and live usability. Catalog evidence applies only to the host it inventories. Working delegation closes the gap; an installed but unloaded extension calls for activation and a live check. Official host examples, including Pi's subagent example, can be recommendations without implying Quartermaster runs under that host. Installation and configuration remain separately approved. Resupply's host-extension route includes native Claude Code mod proposals grounded in current `plugin-authoring` types, with the runtime owner, exact behavior, costs and measured versus inferred savings stated. Each item needs approval, separate user-controlled activation and live usability verification; a completed turn supplies no absence signal. `skills/resupply/evals/evals.json` holds skill-creator scenarios; prose/schema tests do not establish fresh-context recommendation efficacy.
- Cross-plugin use is registry-resolved, never imported: a plugin cannot `require` across plugin roots, so Quartermaster finds Observability through `~/.claude/plugins/installed_plugins.json` and degrades to a no-op when it is absent. Observability uses the same registry to provision project dashboards, and Model Gateway uses it to resolve its stable updater. Small shared helpers are duplicated per plugin instead.
- Bounded schema compatibility: classify all hydrated Codex tools before mutation; admit only proven positive schema/regex contexts, preserve unrelated schema bytes and refuse unsupported affected shapes locally. Ajv Draft 2020 tests compare accepted inputs and authentic prior-adapter fixtures.
- Improvement decisions stay with the orchestrator: research supplies evidence, executors implement the pinned benefit, approach and boundary. Native read-only review/audit/debt recipes remain available on their own.
- Proportional planning and live advice: Sidequest's core skill, `user-story`, `references/ticket-authoring.md` and executor template require feasibility checks before expensive substantial work, with one producer for small deterministic fixes. Assigned builders and readonly advisors can use available native messaging and authorized byte-identified snapshots. Draft findings remain advisory; immutable final capture and independent acceptance keep their own authority. `verify-discipline` keeps touched-function measurement with the producer, allows compatible evidence reuse and pauses only the blocked step.
- The quality gate is project-configured, never a shipped mandate: no Toolshed text requires a CRAP score or a threshold. Quartermaster owns the gate (`skills/setup/references/crap-gate.md`, `.claude/quartermaster/crap.json`, proposed by resupply as an offer); the executor briefing (`src/lib/agentsync.ts`) names the project's configured gate when one exists and the executor runs it and reports rows honestly, otherwise it runs the pinned verifier and says once that no gate is configured and how to add one. An integration hold for missing measurement is valid only when a gate is configured (SQ-3451). The repository's own gate, `scripts/quality/crap.mjs`, discovers functions and computes cyclomatic complexity from the TypeScript AST it already walks (lizard removed; convention in `scripts/quality/README.md`, SQ-3091) and takes `CRAP_PARSER_TRANSPORT=async` to use TypeScript's stdio transport under `node --permission`, where the sync named-pipe transport is refused (SQ-3417). It scores every changed JS/TS file including plugin scripts and test callbacks (SQ-3453) and matches on-file coverage records by position rather than by name, so an executed nested callback never reads 0% (SQ-3461). Quartermaster's language-agnostic gate (`lib/crap-core.cjs`) binds every lizard row to its own definition by span and fails closed on a changed line no row measures, so a lizard misread can neither charge an edit to the wrong function nor let a new function pass unmeasured (SQ-3459).
- A confirmed blocker within delegated scope gets acted on, not just reported: the `user-story` skill's wave-execution guidance dispatches the existing ticket once it is ready, or starts authorized prerequisite preparation, recording the concrete dependency, owner, and resume condition. Unrelated CI or review is not treated as a dependency, and acknowledging or reprioritizing a report does not count as taking ownership of it.
- Terminal inference owns passive readiness: Model Gateway finishes state and telemetry once after retries and existing context-error normalization. HTTP 200 headers cannot establish success; semantic failures retain auth evidence and their actual HTTP status. Normalized context overflow remains a client error, and transient expiry is nonmutating evidence aging rather than proof of recovery.
- Preserve host data without inventing provenance: Quartermaster retains denial kinds and counts, but its report caveat and skills distinguish a host-reported policy block from a proven permission-rule cause. Tool names and reason prose do not supply missing hook provenance. Bare PowerShell fingerprints are excluded from automatic permission recommendations and rechecked before settings writes; existing user allow and deny rules remain untouched, and no scoped PowerShell rule generation is provided.
- Synthetic wiring tests isolate home, environment and cwd so real project settings cannot shadow fixtures. Unknown and confirmed foreign process fixtures supply distinct evidence rather than sharing a null process result.
- RC capability belongs to the serving supervisor: PID-pinned main-loopback control probes and reconciles its configured listener without restarting the worker. Probes close on successful bind and retain cleanup ownership through closure; unavailable or unknown capability refuses enable before hosts writes. Failed activation restores only unchanged command-written hosts bytes, preserving observed external edits. Bound or bindable results report local HTTP transport only; end-to-end Remote Control is documented as unverified for the inspected client versions.
- RC synchronization checks required health before migration, finishes migration before choosing the writable scope, and reports verified settings readback rather than the requested mode. Already-compatible environment-only wiring remains process-limited and creates no settings; disable remains available without a bindability gate.
- Per-board settings a packaged agent definition cannot carry are enforced at hook call time instead: `src/lib/denied-tools.ts` normalizes a board's, category's, or read-only-only `deniedTools` list (never letting it deny the board tools an executor needs to claim and close), and `src/hooks/guard-denied-tools.ts` matches it against every PreToolUse call for the claimed ticket's project and category. `src/hooks/shared/read-only-shell.ts` is the matching lexical guard for shell commands: it is explicitly not a sandbox, only a catch for the shell forms an agent reaches for to edit files, because the session's own `bypassPermissions` mode (which read-only executors inherit, since Claude Code ignores an agent file's own `permissionMode`) is the real write authority.
- The Windows Sandbox harness (`sandbox/windows/`, gitignored, maintainer-only) maps only its bootstrap directory read-only and tests isolation and feature flags before launch.
