# Onboarding

Last Updated: 2026-09-10

1. Read `README.md`, `CLAUDE.md`, and this map index. `CLAUDE.md` contains repository rules for generated docs, prose docs, and synthetic screenshots.
2. Identify the surface: Sidequest engine/dashboard, Quartermaster, Observability, Model Gateway, Live-rules, Codebase Mapper, shared test support, docs, the local-only Windows Sandbox harness, or release automation. Start with [entry-points](entry-points.md) and [modules](modules.md).
3. For Sidequest runtime work, read `plugins/sidequest/package.json`, `plugins/sidequest/scripts/build.mjs`, and `plugins/sidequest/scripts/generate-bundled-agents.mjs`, then the relevant source module. Remember manifests load committed `agents/`, `lib/`, `bin/`, and `hooks/` output; normal session-start maintenance migrates marked legacy generated agents instead of recreating them.
4. For Sidequest lifecycle work, start with `plugins/sidequest/src/lib/kernel/`, including `kernel/review-binding.ts`, then follow the adapter into `store/dispatch.ts`, `store/submissions.ts`, or `worktrees.ts`. `prepared-dispatch.ts` canonicalizes prepared executor identity, and `source-revision-capability.ts` binds immutable non-Git candidates to their dispatch baseline. Frozen briefing snapshots are continued with the `context_page` MCP tool. Commandless shared-tree delivery records typed `done.verify` evidence for non-command requirements, while command and suite requirements need the matching verify-capture; primary SessionStart reconciles launched dispatches that never bound an agent or claim. Reduced Agent-schema dispatch omits `name` and `mode`, then requires hook-reported `agent_id` and `permission_mode` `bypassPermissions` before the first claim.
5. For Model Gateway work, start at `plugins/model-gateway/README.md` and `plugins/model-gateway/bin/model-gateway.js`; use `doctor` and readiness/catalog checks when verifying local setup. Sidequest consumes only fresh schema-4 catalogs whose provider readiness is true. Shared-proxy recovery belongs in `lib/process-supervision.js` and `lib/request-worker.js`, not in project-specific startup hooks. Same-marketplace/plugin cache siblings may be replaced during upgrade, while foreign or non-cache processes stay untouched; startup, recovery, restart, and drain leave unknown ownership untouched, and POSIX ownership probes use `ps -ww` to preserve full command lines. Any per-model window or compaction number comes from `lib/runtime.js` `resolveGatewayModelPolicy`; never add a second copy. When the gateway "died", read `doctor`'s lifecycle evidence before theorizing. Discovery and cache cleanup both normalize IDs through `lib/runtime.js` `gatewayClientModelId`; open sessions can retain old picker rows until restarted. A concrete custom agent model belongs in its frontmatter and is invoked through `subagent_type` without an `Agent.model` override, whose host enum cannot accept arbitrary gateway IDs. Desktop 1.49585.0 native Gateway configuration can select the endpoint but locally rejects GPT/Codex model families, even with explicit model entries; the CLI is the verified Codex path.
6. Run the narrow package check or test command documented in that package before broad suites. Sidequest scripts include `typecheck`, `build:check`, `test:files`, `test:full`, and `test:perf`; dashboard has `check`, `test`, `build`, and `e2e`; Quartermaster setup validates the Sidequest registry, derives routing profiles, requires an explicit worktree-isolation choice, applies profiles/worktrees in Phase 4, seeds an adapted reuse-first implementation baseline and self-improvement live rule, and checks effective `autoCompactWindow`; setup may offer 325000 when unset, while doctor reports it read-only. Its update skill uses the stable Model Gateway updater. Docs uses `npm --prefix docs run check`, and `npm --prefix docs run build` on top of it whenever a page or sidebar entry is added, renamed, or removed, because `check` passes on a sidebar slug whose page no longer exists; the sandbox contract uses `pwsh -NoProfile -File sandbox/windows/Test-ToolshedSandbox.ps1`.
7. The clean-code baseline lives only in `plugins/quartermaster/skills/setup/references/clean-code-principles.md`; setup seeds it as a live rule. Quartermaster never imports another injector's preferences or disables it automatically.
8. For user-facing changes, update affected prose docs in `docs/src/content/docs/` or file the linked docs-writing ticket. Never hand-edit generated reference pages.
9. For plugin changes, update both plugin manifest and marketplace version fields through the release process. See [release and publishing](release-publishing.md).
