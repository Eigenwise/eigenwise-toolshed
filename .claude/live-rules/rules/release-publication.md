description: Automated release policy

- `main` and `develop` are both protected: PR + required checks, admins included, no force-push. Nothing pushes either branch directly. Integrate ticket work on `develop`; `main` only ever receives a release promotion PR.
- Write a release fragment in the same push as the ticket work with `node scripts/release/note.mjs <REF> --plugins <p> --bump <level> --commit <sha>`. Executors author their own `.release/unreleased/<REF>.md` when a submission changes a published plugin; Sidequest grants only the matching ticket fragment.
- Versions, tags, and changelog edits are release-owned; only `scripts/release/cut.mjs` writes versions, and in the protected flow used here only `scripts/release/finalize.mjs` creates tags. The direct `cut.mjs --push --direct-publish` path still tags too; it is off by default and never used on this repository.
- Releasing is three explicit commands, never one:
  1. `node scripts/release/cut.mjs --prepare --push` from a clean `develop`. It builds the window on `release/v<version>`, runs the changed plugins' suites, creates NO tag, and leaves `main` and `develop` untouched. `--dry-run` first.
  2. Open and merge the promotion PR it prints (`gh pr create --base main --head release/v<version>`) once the required checks pass. The PR is the only thing that moves `main`.
  3. `node scripts/release/finalize.mjs --push` after the merge. It tags the exact merged `main` head and pushes only tags. It refuses an unmerged or wrong sha, refuses a failed or missing Test run on that sha, refuses a version delta that is not against the first parent, refuses a publish branch that moved while it was validating, refuses to move an existing tag, and is a no-op once the tags are published. None of those refusals has an override.
- Then sync `main` back to `develop` through the PR `finalize.mjs` prints, and merge it BEFORE the next feature PR: until it lands, `develop` carries older versions than `main` and every PR into `develop` fails the release guard's version check. The guard recognises that sync PR from the forge's own base/head repository and refs, then waives each release-owned path only where the PR's resulting tree holds exactly the entry the pinned `main` commit published, never from its branch name. So build it as a plain merge of `main` into a branch off `develop` and amend nothing on top: any edit riding that merge, even to a manifest, keeps its ordinary fragment requirement.
- `--push` acquires the Sidequest publish lock before it changes anything and releases it after; a held lock stops before the release window changes.
- `.github/workflows/release.yml` is the sole GitHub Release publisher. It handles `v*` tag pushes, daily catch-up, and manual dispatch, with a one-Release-per-UTC-day cap.
- `cut.mjs --push` without `--prepare` would push `main` directly. It now refuses unless you also pass `--direct-publish`, which exists only for a repository whose publish branch is unprotected. Never reach for it, or for `--no-branch-check`, here: use the prepare/promote/finalize flow.
- The publish lock serialises releases run through Sidequest. It cannot stop an unrelated writer pushing `main` from elsewhere, and git offers no tag push that is conditional on a branch it does not update, so `finalize.mjs` re-reads `main` inside the lock immediately before tagging (refusing on movement) and again after the push (reporting it). That is the honest limit of the guarantee; nothing here force-pushes a protected branch to close it.
